# M0 基线对照与偏差清单（2026-11-05）

> **对照对象**：`docs/baseline-m0.md`（冻结版） vs 当前仓库 `v0.6.1` 与 [迭代计划](iteration-plan.md)。
> **结论**：当前实现覆盖了 M1 + M2 的大部分能力，但**不是一份可直接按 M0 验收的 M1/M2 交付**；5 处基线问题已按 2026-11-05 默认决策登记，M3 核心已实现。
> **图例**：✅ 符合；🟡 部分符合/实现细节待修；🔴 缺失或与基线冲突；❓ 待确认。
> **实施进度（2026-11-05，更新至 2026-11-11）**：M1 补丁 + M3 核心联动已落地（`fold`/`composeMonitor`、未知终态、告警吸顶、步数展示、`agent:*` 信号、审批暂停、+5/+50）。逐条验收见 [m1-acceptance.md](m1-acceptance.md) 与 [m3-implementation.md](m3-implementation.md)。0.5.0–0.6.1 追加：D28 question/plan 分 kind 告警、低调模式（胶囊/浮动小窗/后台通知）、五子棋高级难度。下文的"当前实现"指 `v0.4.1`，为撰写时快照。

## 1. 一句话判断

**不建议现在从零准备 M1 工程脚手架。** 仓库已经是 M1+M2 的实现（还提前做了 M4 的五子棋/设置），真正缺的是：

1. 按 M0 逐条验收 M1/M2，修掉告警、状态、步数展示、软按钮等偏差；
2. 补 M3 剩余的桌面端验收与工程项（信号核心已落地）；
3. 把 M0 之后新增的决策（D7/D9/D16/D17）正式登记为"已批准偏离"，否则无法声称"对照 M0 验收通过"。

从零搭 M1 会重复已有的 Session View、投影、看板代码，而且会把现有问题一起带进新骨架。

## 3. 已按默认拍板的 5 个基线问题

> **2026-11-05 结论**：D7 保留（已批准偏离）、D16/D17 保留（M4 提前实现）、D22 保持 `aborted` + 原因、步数保留；D28 question/plan 已于 0.5.0 落地（分 kind 告警 + 游戏自动暂停）。以下保留原始决策过程。

### 3.1 question / plan-review 是否纳入

- **M0 原文**：§6 的最小事件集只有 `session.tool.pending_approval`；§11 说新增事件走需求评审。
- **三份评审都建议**：把 `question` / `plan-review` 也显示为"等待你处理"。
- **结论**：这是**范围扩展，不是基线内 bug**。如果要做，应登记为 D28"阻塞交互泛化"并明确它属于 M1/M2/M3 之外的增强；如果不做，M1 验收只要求 approval 可见。当前计划里的 ST-03 需要拆成：
  - **P0**：approval 可见 + 告警吸顶（基线内）；
  - **P1/提案**：question / plan-review 可见（需批准）。

### 3.2 五子棋（D16）与设置持久化（D17）是否保留

- **M0 原文**：§10 把"多游戏切换"和"分数本地持久化"列为 M4 备选，不在基线强制排期。
- **当前实现**：五子棋、速度/难度设置与 `localStorage` 持久化已经上线（M1 补丁未改动）。
- **结论**：这是**提前实现的 M4 范围**。需要明确：
  - **保留**：登记 D16/D17 为产品负责人批准的偏离，并在 M1/M2/M3 验收中声明"不作为基线能力"；
  - **收缩**：如果要严格按 M0 交付，需在 M1/M2 验收版本隐藏五子棋/设置（feature flag 或分支）。
- **建议**：保留 + 登记偏离。功能已经存在，移除的收益低于维护成本；但不要再把它算作"M1/M2 达标"的证据。

### 3.3 软按钮（D7）是否恢复

- **M0 原文**：§5 明确"画布内附带软按钮，规避 WebView 键盘捕获冲突"。
- **当前实现**：D7 以"产品负责人明确要求不需要软键盘"为由移除。
- **结论**：这是**明确的基线偏离**。需要二选一：
  - **恢复软按钮**：符合 M0，但违背 D7 记录的产品要求；
  - **保留 D7**：把 D7 标注为"产品负责人批准、替代 M0 §5 的正式偏离"，并在 M1/M2 验收记录中写明。
- **建议**：保留 D7 + 正式登记偏离。触屏/纯鼠标不可操作是已知代价，M0 §5 的软按钮本来就是为了这个场景；如果目标用户包含触屏，建议恢复。

### 3.4 步数展示（D1/D9）是否恢复

- **M0 原文**：§6 明确"仅展示 stepCount"，状态文案"执行Step N / 总步数未知"；§8 的 TrackState 也包含 `stepCount`。
- **D1**：去掉"总步数未知"，保留"已完成 N 步"（与 M0 兼容）。
- **D9**：进一步隐藏步数，改为活动流（与 M0 §6 冲突）。
- **当前实现（M1 补丁后）**：已恢复「已完成 N 步」；D9 的"完全隐藏"作为待确认偏离保留。
- **结论**：这是**比 D7 更直接的验收冲突**。需要二选一：
  - **按 M0 验收**：恢复 `已完成 N 步` 元信息（可保留 D1 的"不显示总步数"），活动流作为补充；
  - **按 D9 验收**：把 D9 登记为正式偏离，并在 M1 验收标准中改写 §6 的步数文案。
- **建议**：恢复 `已完成 N 步`（D1），保留活动流。这样同时满足 M0 §6 和"不做假进度"；D9 的"只显示活动流"作为可选展示模式，而不是默认。

### 3.5 新增状态（unknown / awaiting_user / degraded / stale）怎么处理

- **M0 原文**：§8 的 `status` 是六值封闭枚举。
- **早期计划/评审建议的写法**：新增 `awaiting_user`、`unknown`、`degraded`、`stale` 作为 status，会直接改变 M0 状态模型。
- **兼容做法（推荐）**：
  - `status` 保持六值；`pending_approval` 不变，新增 `pendingKind: 'approval' | 'question' | 'plan-review' | 'unknown'` 作为**展示子字段**；
  - 新增 `health: 'loading' | 'ready' | 'degraded' | 'stale'` 作为**数据健康字段**，不进入 `status`；UI 在 health 非 ready 时覆盖状态行文案，避免显示"空闲"；
  - 未知 `turn/end` reason：在六值内没有诚实的映射。两个选项：
    - **推荐**：登记 D22，给 `status` 增加 `unknown`（需产品负责人批准，因为改枚举）；文案"本轮已结束（原因：X）"，中性色；
    - **不改枚举**：映射到 `aborted`，但 UI 文案写"本轮已结束（未知原因）"，`aborted` 仅作为内部承载。这样状态字段不完全诚实，但 UI 不撒谎。
- **建议**：先按"不改枚举"实现 `pendingKind`/`health`；`unknown` 单独走 D22 申请。如果产品负责人希望完全诚实，批准 D22。

## 5. 建议的下一步

### 如果目标是"M1 可验收"

1. **不要从零搭脚手架**；在现有 `v0.4.1` 上做 M1 对照。
2. 先确认 3.1–3.5 的 5 个冲突（其中 3.5 是设计选择，不是产品取舍）。
3. 做一次 1–2 天的 M1 验收补丁：
   - 告警吸顶（AT-01）；
   - 状态真实性（ST-01/02/04）；
   - 按决定恢复/隐藏 stepCount（3.4）；
   - 按决定恢复/登记软按钮（3.3）；
   - 补 `fold`/`compose` 单测（QA-01）。
4. 产出一份"M1 对照验收记录"，逐条引用 M0 §x。

### 如果目标是"M3 闭环"

在 M1 对照通过后，直接进迭代 2：

- 信号层按 `agent:task_start`、`agent:step_advance`、`agent:approval_enter`、`agent:approval_leave`、`agent:task_finish` 定稿；
- 贪吃蛇按 M0 §9 实现 +5 / +50 / 失败提示 / 审批暂停 + 手动恢复；
- 补 `pauseReasons` + `manualPaused`；
- 补双实例、切会话、连续审批的回归。

### 如果坚持"从零重写 M1"

可以，但要明确：
- 这是一条新分支/新仓库，不是当前 `v0.4.1` 的迭代；
- 现有 M2/M3 代码、评审修复、用户数据（localStorage 设置）需要迁移；
- 不建议在没有明确收益的情况下做，因为 M1 的核心（Session View + 投影 + 看板）已经存在且可用。
