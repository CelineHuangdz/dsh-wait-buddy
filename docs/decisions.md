# 决策记录（ADR-lite）

> 规则：**先改文档，再改代码**。每条决策记录"结论 + 理由 + 影响面"；被推翻时保留原文并标注状态。
> M0 基线保持冻结：这里记录的是**显示文案 / 布局 / 实现边界**的调整，涉及基线语义的改动必须显式标注。

> **M0 基线（2026-11-05 补录）**：原文见 [baseline-m0.md](baseline-m0.md)。D7（软按钮）、D9（隐藏步数）、D16（五子棋）、D17（设置持久化）与 M0 §5/§6/§10 存在偏离，待产品负责人确认；逐条对照见 [m0-compliance.md](m0-compliance.md)。

## D1 进度文案：去掉「总步数未知」（2026-11-04，生效）

**结论**：运行中状态文本改为「正在执行任务」，步数移入右侧元信息「已完成 N 步」；不再出现「总步数未知」，也不引入任何百分比。

**理由**：
- DSH 的 Agent 循环是开放式循环：每一步由模型决定是否继续，日志里**没有**预先声明的总步数；即使把会话事件全订阅一遍也拿不到分母。
- M0 §2 明确禁止"强行估算精准百分比进度"；"未知"只是把这件事暴露在文案里，观感差且无信息量。
- 步数本身仍然真实（`step/end` 计数），只是不再暗示存在一个已知总数。

**影响面**：仅 Client 文案与布局。Host 投影 `waitbuddy` 不变，事件映射不变。

**备选（未采纳）**：用 Agent 的 Todo 列表做真实分母（「待办 3/6」）。前提是 Agent 维护了 todo；属于新增投影依赖，需单独立项，见 D5。

## D2 不替换、不隐藏会话输入框（2026-11-04，生效）

**结论**：WaitBuddy 视图保留 shell 的 composer 与 Todo dock，不尝试移除。

**理由**：唯一能做的是注册 `conversation.composer.bar`（single slot）shadow 原生 composer，这会同时破坏输入、队列、附件与审批接管，属于 `shadows-shipped-ui` 的高风险替换；且单槽无法"只在 WaitBuddy 激活时隐藏"。
若需要完全无 chrome 的界面，应走 M0 §10 备选池的"悬浮独立浮窗"，而不是占用视图槽。

## D3 去卡片化：一屏只保留一个表面（2026-11-04，生效）

**结论**：移除状态卡与游戏卡的外层卡片；状态条改为排版 + 发丝线，游戏区只保留棋盘这一层表面；内容统一左对齐成柱（max 680）。

**理由**：上一版出现"大横框里套深色方块"的三层矩形（页面 / 卡片 / 棋盘），且状态卡与游戏卡宽度不一致、都居中，视觉上对不齐。减少容器层级比增加装饰更能提升观感。

**影响面**：`client.js` 结构类名与 CSS；交互不变。

## D4 棋盘尺寸随视口高度（2026-11-04，生效）

**结论**：`clamp(220px, 44vh, 420px)`；右侧列 168px；窄窗口整列换行。

**理由**：固定像素在矮窗口会溢出、在高窗口显得小；用视口高度驱动可以在不滚动的预算内尽量放大棋盘，并保留 200px 的可玩下限。

## D5（提案，未采纳）Todo 作为真实分母

**结论**：暂不做。若 `todo` 投影存在且当前轮有未完成项，可显示「待办 3/6」作为真实进度；需要确认投影 key 与语义，并写入基线后实施。

## D6 变更流程：先文档后代码（2026-11-04，生效）

**结论**：任何界面、文案、事件映射、信号契约的变更，先更新 `docs/ui-spec.md` 或本文件（必要时同步 README），再改代码；提交说明需同时指向文档条目。

**理由**：M0 基线冻结后，文档是唯一的"当前版本事实"；先文档后代码避免实现漂移，也让评审能先看结论。

## D7 去掉软方向键，只保留键盘方向键（2026-11-04，已批准偏离 2026-11-05）

> **M0 对照**：M0 §5 要求画布内软按钮；本决策与基线冲突。
> **2026-11-05 默认决策**：保留 D7；不恢复软按钮，登记为 M0 §5 的已批准偏离（触屏/纯鼠标设备无法控制方向，已知并接受）。

**结论**：移除棋盘旁的软 D-pad；方向控制只保留键盘方向键（焦点在视图内时生效）。保留「暂停 / 重置」普通按钮与浮层主按钮。

**理由**：产品负责人明确要求"不需要软键盘，就用方向键即可"。方向键仍做焦点作用域限制，不会抢输入框的按键。

**与基线的关系**：M0 §5「键盘方向键控制，画布内附带软按钮，规避 WebView 键盘捕获冲突」中的软按钮要求**由产品负责人明确取消**；其余约束（Canvas、无外部资源、独立状态）不变。

**代价**：触屏 / 纯鼠标设备无法控制方向，已知并接受。

## D8 整宽双栏看板（2026-11-04，生效）

**结论**：取消 680px 居中窄栏；改为占满会话视图宽度的双栏布局——左栏监控（状态 / 脉冲 / 最近动作），右栏游戏（棋盘 + 三行说明），窄窗口右栏换行到下方。

**理由**：Trajectory 等宿主视图铺满宽度，窄栏居中会让内容显得"困在中间"，且右侧大片空白无法利用。游戏是方格，宽度不可无限放大，因此把横向空间交给监控栏、纵向空间留给棋盘。

**影响面**：`client.js` 结构与 CSS；交互、事件映射、Host 投影均不变。

## D9 用「活动流」补充步数显示（2026-11-04，M1 修订：保留步数、移除推理）

> **M0 对照**：M0 §6 要求展示 `stepCount`。M1 已恢复「已完成 N 步」元信息（D21）；2026-11-05 默认决策不采纳 D9 的「完全隐藏步数」，活动流继续作为补充。
>
> **2026-11-05 二次修订（D27）**：`assistant/message` 的 reasoning 不再进入活动流；活动流只保留 `tool/call` 的命令/工具条目。下面 D9 原文中的 `thinking` 映射仅作历史记录。
> **2026-11-05 默认决策**：D9 的“完全隐藏步数”不采纳；保留 D21 的「已完成 N 步」，活动流作为补充。

**结论**：界面不再显示步数（既没有总数，也不强调单步计数）；改为展示最近的真实活动——思考（reasoning）、命令（bash 类工具调用）、工具调用（其它工具）。

**理由**：产品负责人指出"没有步数就不要硬显示步数"。Agent 循环没有可靠分母，单纯递增的数字对等待中的人没有信息量；活动流直接回答"它现在在干什么"。

**事件集变更**：在 M0 §6 最小事件集之外，新增订阅 `assistant/message`（提取 reasoning 块）。该扩展由产品负责人明确要求，记录在案；`step/end` 仍保留用于内部步数计数（M3 计分用），但不再进入界面。

**映射**：
- `assistant/message`（含 reasoning）→ `thinking`
- `tool/call` 且参数含 `command` → `command`
- 其它 `tool/call` → `tool`

**约束**：最多 3 条、每条截断 120 字符、相邻重复不追加、`turn/start` 清空。

**隐私提示**：思考内容来自模型 reasoning，会以截断文本显示在本会话面板中；如不希望展示，可把 `thinking` 从活动流移除（只需改 Host fold 与文案，不影响其它结构）。

## D10 上下分区、整宽铺满（2026-11-04，生效）

**结论**：撤销 D8 的左右双栏；状态区在上、游戏区在下，两段都占满视图宽度。

**理由**：产品负责人要求"不要状态和游戏区左右排，而是上下排，横向尽可能拉宽"。上下分区也让阅读顺序与"监控优先"一致。

## D11 棋盘改为宽屏长方形（48×16，3:1）（2026-11-04，生效）

**结论**：棋盘从 18×18 正方形改为 48 列 × 16 行、3:1 宽屏长方形；宽度 `min(100%, 120vh, 1080px)`（高度上限约 40vh），占满可用横向空间；说明行移到棋盘下方。

**理由**：产品负责人两次指出"游戏区还是很小很窄"。正方形棋盘受窗口高度限制，宽度只能到 300px 左右，在 900+px 宽的视图里必然留下大片空白；改成宽屏长方形后，同样的 ~290px 高度可以换来 ~870px 宽度，横向铺满且不增加垂直占用。

**约束**：格子保持正方形（48×16 与 3:1 严格对应），不做非等比拉伸；显示尺寸随容器等比缩放，画布逻辑尺寸 864×288、2× 后备缓冲。

**影响面**：游戏逻辑的边界（cols/rows）、初始蛇位置、食物生成、绘制尺寸；事件映射与 Host 投影不变。

## D12 棋盘改为「宽度 100% + 实测格数」（2026-11-04，生效）

**结论**：棋盘宽度不再用固定宽高比推算，而是 `width:100%; height:min(40vh,360px)`；格数在布局后按实测像素推导（约 18px 一格，列数 16–120、行数 ≥8），绘制用实际 `cellW/cellH`，格子保持近似正方形。

**理由**：D11 的 3:1 仍受 `120vh` 上限约束，在 1247px 宽的视图里只用了约 73% 的横向空间。要"永远吃满宽度"，宽高比就只能是推导结果而不是输入；把格数交给实测尺寸后，棋盘宽度 100%、高度固定，写死的比例被彻底移除。

**约束**：在对局（running/paused）期间不重新推导格数，避免蛇/食物坐标越界；只有 idle/over 时才随容器 resize 重建网格。格子为近似正方形（列宽/行高由同一像素预算推导，误差 ≤1px）。

**影响面**：游戏状态的网格从常量变为 state 字段；Host 投影与事件映射不变。

## D14 任务结束后的「查看对话」按钮（2026-11-04，生效）

**结论**：本轮结束（success / failed / aborted）时，状态行末尾展示次级按钮「查看对话」，点击通过 `conversation.view` 的 `openView('chat', '')` 切回对话视图。

**理由**：产品负责人希望任务完成后能一键回到对话看结果。这是纯视图导航，不发送消息、不取消/重试、不干预审批，因此不违反 M0 §2「不反向控制 Agent」；按钮仅在终态出现，运行中不打扰。

**边界**：只依赖宿主的 View 选择能力；若 `openView` 缺失则不渲染按钮（能力缺失时静默降级）。切换视图会暂停游戏（既有行为），进度保留。

**影响面**：Client 状态行新增一个按钮与一条文案；Host 投影、事件映射不变。

## D15 对话页增加「休息一下」入口（2026-11-04，**已撤销**）

> **状态：已撤销。** 产品负责人明确表示不要这个功能：入口位置（视图标签栏的「…」菜单）不是想要的位置，功能整体移除。保留本记录作为决策历史，代码与界面中不再存在该入口。

**结论**：在 `conversation.session.header.views.actions`（视图标签栏的「…」菜单）注册一行「休息一下（WaitBuddy）」，点击 `onOpen('waitbuddy')` 切到 WaitBuddy 视图。

**为什么不在输入框旁放按钮**：从 Bundle 代码确认，视图选择由会话级 `conversationStore` 的 `view` 驱动，唯一写入口是 `conversation.session` 注入的 `actions.setView`，它只暴露给两处——`conversation.view` 条目（`openView`）和这个菜单行（`onOpen`）。`conversation.input.*`、`conversation.composer.dock` 等槽位只拿得到标准 Session 属性，**没有** view 选择能力；`uiConversation.binding(id).activate()` 只激活数据目标、不改渲染选择。
因此要么用菜单行（受支持），要么依赖未公开的 store 写入（不做）。

**替代方案（已存在）**：标签栏里的 WaitBuddy 标签本身就是一次点击直达；菜单行是给"想从对话页显式找入口"的场景补的标签。

**影响面**：仅 Client 注册一个新槽位条目 + 一个按钮样式；不影响投影与事件。

## D16 增加第二款游戏「五子棋」（2026-11-04，已批准偏离 2026-11-05）

> **M0 对照**：M0 §10 把多游戏切换列为 M4 备选。本功能已提前实现；**2026-11-05 默认决策**：保留并登记为 M4 提前实现，不计入 M1-M3 基线达标。

**结论**：在 WaitBuddy 游戏区增加 15×15 五子棋（人执黑 vs 简单启发式电脑），与贪吃蛇通过说明行左侧的两个页签切换，共用同一棋盘容器。

**与基线的关系**：M0 §10 把"多游戏切换（2048、消消乐）"列为 M4 备选；本次由产品负责人直接要求先加五子棋。因此"D16 起游戏区支持多游戏切换"，切换形态保持轻量（两个页签），不引入游戏 SDK、不引入设置项。

**AI 说明**：无第三方库，纯前端启发式——先确保自己成五、再堵对方成五，否则按四个方向的连子数/开口数加权选点；候选点限制在已有棋子周围 2 格内以控制计算量。对局是同步计算（点击后立即落子），不占用主线程动画。

**边界**：不做难度、悔棋、计时、联网；五子棋不参与 M3 的 `agent:*` 联动（联动仍只作用于贪吃蛇预设行为）。切换游戏会保留双方对局；切到五子棋时贪吃蛇自动暂停。

**影响面**：Client 新增五子棋状态机/绘制/页签；Host 投影与事件映射不变。

## D17 游戏设置：贪吃蛇起始速度 + 五子棋难度（2026-11-04，已批准偏离 2026-11-05）

> **M0 对照**：M0 §10 把分数/设置持久化列为 M4 备选。本功能已提前实现；**2026-11-05 默认决策**：保留并登记为 M4 提前实现，不计入 M1-M3 基线达标。

**结论**：游戏区说明行增加设置分组——贪吃蛇「速度」三档（慢/标准/快），五子棋「难度」三档（初级/中级/高级）。设置保存在 `localStorage` 的 `dsh-wait-buddy.settings.v1`，刷新后保留。

**参数**：
- 速度：慢 `200ms 起 / 110ms 下限 / 每果 -5ms`；标准 `140 / 70 / -4`；快 `100 / 55 / -3`。
- 难度：初级 `候选半径1 / 防守权重0.35 / 前三随机`；中级 `半径2 / 防守0.9 / 取最优`；高级 `半径3 / 防守1.15 / 最优 + 双威胁加权`。三档都会堵对方成五（不故意送胜），强弱差异来自候选范围、防守权重与随机度。

**为什么放界面而不是 Host Config**：这是玩家口味偏好，不是部署/能力开关；用 `cordis.patch.yml` 改需要重启 profile，体验不合适。Host Config 仍留给真正的部署参数。

**边界**：只持久化设置，不持久化分数/棋局（M0 §10 的"分数本地持久化"仍是备选池项）。设置仅存于本机浏览器，不随会话同步。

**影响面**：Client 新增设置 store 与分段按钮；Host 投影、事件映射不变。

## D18 可点击控件与纯文本标签的视觉区分（2026-11-04，生效）

**结论**：游戏区的所有可选项统一改成**分段控件**（外描边胶囊 + 内分隔线 + 选中填充），「速度」「难度」这类不可点击的文字保持无边框纯文本；单个动作按钮仍是带描边的 `.wb-btn`。

**理由**：上一版未选中的分段按钮是"透明背景 + 次要色 + 无描边"，与「速度」标签的样式几乎一致，用户无法判断哪些能点。给整组加一个外框后，"框里的能点、框外的只是标签"，同时选中态也更明确。

**约束**：分段控件只用 `--dsw-alias-*` 令牌；选中态用背景 + 主文本色，不引入品牌色，避免和主按钮抢注意力。

**影响面**：仅 `client.js` 的结构与 CSS、ui-spec 排版表；交互逻辑不变。

## D19 棋盘吃满剩余高度（2026-11-04，生效）

**结论**：游戏棋盘高度从固定 `min(40vh,360px)` 改为**弹性填充**：`.wb-inner` 撑满视图高度，`.wb-game` 与棋盘 `flex:1`，基准 `min(46vh,480px)`、下限 200px、上限 520px。

**理由**：截图里说明行下方还有约 100px 空白——面板是内容高度，棋盘又写死 40vh，剩余空间没人用。改成弹性后棋盘随窗口高度增长，说明行贴在其下方。

**回退保护**：若宿主视图容器高度不确定（`height:100%` 解析为 auto），棋盘退回 `min(46vh,480px)` 基准，仍比原 40vh 大，不会变小。

**影响面**：仅 CSS；贪吃蛇按新高度重推格数，五子棋方形棋盘按新高度居中。

## D20 以不带 scope 的 `dsh-wait-buddy` 发布（2026-11-04，生效）

**结论**：以公共 npm 包 `dsh-wait-buddy` 发布，不用 scoped 包名；`private` 移除，首发版本 `0.3.0`。

**理由**：`npm view dsh-wait-buddy version` 返回 404，名字可用；不带 scope 对使用者最短、最好记。包名同时是 Client 模块 id，三处（`package.json`、`cordis.patch.yml`、`client.js`）保持一致。

**发布源**：本机 npm/pnpm 默认指向 `registry.npmmirror.com`（只读镜像），已在 `package.json` 设 `publishConfig.registry = https://registry.npmjs.org/`，发布只走官方源。

**回退**：若后续需要组织命名空间，可改发 `@scope/dsh-wait-buddy`，同时修改上述三处与 README 的安装说明。

**影响面**：仅发布配置与文档；插件运行时行为不变。

## D21 M1 按 M0 §6 恢复「已完成 N 步」（2026-11-05，生效）

**结论**：状态行右侧元信息显示「更新于 HH:MM:SS · 已完成 N 步」；N 来自 Host `step/end` 的真实计数；不显示总步数、不显示百分比。步数为 0 时省略。

**理由**：M0 §6 明确"仅展示 stepCount"；D1 也保留了「已完成 N 步」。D9 的"完全隐藏步数"与 M0 §6 冲突，先按基线恢复展示，D9 转为待确认偏离。

**影响面**：仅 Client 文案与 `metaText`；Host 投影字段不变。

## D22 未知 `turn/end` 原因映射为 `aborted` + 原因文本（2026-11-05，生效）

**结论**：只有显式 `completed` 才映射为 `success`；未知 `reason.kind` 映射为 `aborted`，`errorMessage` 记录「未知结束原因：<kind>」，UI 显示「本轮已结束（未知原因）」。不新增 `unknown` status，M0 §8 的六值枚举不变。

**理由**：基线冻结了 `status` 六值；把未知原因判成功会撒谎，新增枚举又需要基线变更。用 `aborted` 承载中性终态、用文案区分，是当前约束下最不坏的方案。

**2026-11-05 默认决策**：保持 `aborted` + `endReason`，不新增 `unknown`。

**备选（未采纳）**：新增 `unknown` status（需单独立项并批准基线变更），同时把 `stateVersion` 升到 5；批准后可替换本方案。

**影响面**：Host `endedWith`/`fold`、`stateVersion` 当前为 4；若新增 `unknown` 则升到 5。Client `statusText`。

## D23 M1 用 `health` / `pendingKind` 承载展示扩展（2026-11-05，生效）

**结论**：M0 的 `status` 保持六值；Client 快照新增 `health`（`loading`/`ready`/`degraded`/`stale`）与 `pendingKind`（当前仅 `approval`）作为展示字段，不写入 Host 投影。

**理由**：需要在投影缺失、Host 断开、审批等待时给出准确文案，但不能改 M0 的状态枚举；展示字段可以在不改基线的情况下满足"不撒谎"。

**边界**：`health` 不能覆盖 approval/failed 的高告警文案；`pendingKind` 的 question/plan-review 需要 D28 扩展批准后才启用。

**影响面**：`composeMonitor`、`sameMonitor`、状态行文案；Host schema 不变。

## D24 告警条独立顶部区域（2026-11-05，生效）

**结论**：告警条移出 `.wb-inner` 滚动容器，作为 `.wb-root` 的独立顶部区域；`.wb-root` 改为 flex column，`.wb-inner` 负责滚动。告警常驻可见，不随内容滚动；`.wb-alertTitle` 允许换行。

**理由**：ui-spec 要求"告警不依赖滚动可见"，M0 §7 要求高告警是醒目辅助提醒；普通文档流在矮窗口/棋盘滚动后会失效。

**影响面**：Client 布局/CSS；无事件映射变化。桌面端视觉验收见 `docs/m1-acceptance.md`。

## D25 M3 `agent:*` 信号层与审批暂停（2026-11-05，生效）

**结论**：监控层只发五类 `agent:*` 信号（task_start / step_advance / approval_enter / approval_leave / task_finish）；`SignalHub` 按 `type + sessionId + key` 去重；首个 ready 快照作为 baseline，不补发历史奖励，但已有 approval 会补发一次 enter。游戏 store 用 `pauseReasons` + `manualPaused` 管理暂停：审批进入自动暂停，审批消失不自动恢复，由用户手动继续。

**理由**：M0 §9 要求"监控不定义奖励、游戏自主消费"；M0 §9 还明确审批处理后由用户手动恢复。把暂停原因做成集合，能处理连续审批、手动暂停、视图隐藏等叠加情况，避免"审批结束就把手动暂停的局跑起来"。

**影响面**：`client.js` 新增 `diffMonitorSignals` / `createSignalHub` / `gameStore.handleSignal`；M3 奖励 +5/+50；UI 增加审批浮层、浮字、toast。

**边界**：question/plan-review 不在 M0 §9 的五类信号内，未接入；跨会话奖励叠加按 M0 §8 保留。

## D26 切会话时暂停游戏（2026-11-05，生效）

**结论**：`GameArea` 监听 `sessionId` 变化，切换会话时调用 `gameStore.pauseWithHint('session-switch')`，保留进度并显示「切换会话后已暂停」；不重置游戏。

**理由**：M0 §8 要求切会话只重置监控状态、游戏状态保留；ui-spec 要求切会话暂停。此前 `WaitBuddyView` 复用、`GameArea` 不卸载，游戏会继续跑。

**影响面**：仅 Client；多实例/按会话存档仍不在本次范围。

## D27 移除活动流中的模型推理原文（2026-11-05，生效）

**结论**：Host 不再订阅/折叠 `assistant/message` 的 reasoning；活动流只显示 `tool/call` 的命令或工具名 + 参数摘要。`ACTIVITY_KINDS` 收窄为 `command` / `tool`，Host 投影 `stateVersion` 升到 4，旧缓存中的 `thinking` 条目在重算后消失。

**理由**：
- 截图里面板直接显示了模型的内部推理（"Need decide whether to continue further..."），属于链式思考原文，不适合在共享屏幕/录屏中展示；
- M0 §6 的最小事件集不包含 `assistant/message`，D9 的 reasoning 扩展本来就是基线外偏离；
- 活动流要回答"它在干什么"，工具/命令已经足够；推理原文信息密度低且可能包含敏感内容。

**影响面**：`index.js` fold/stateSchema、`stateVersion` 4；`client.js` 活动流文案；README/ui-spec/测试。

**回退**：如果以后确实需要"思考摘要"，应作为显式 opt-in（默认关闭）并通过 Host 侧脱敏，而不是恢复原文。

## D28 question / plan-review 暂不纳入基线（2026-11-05，按默认）

**结论**：当前只把 `pendingInteraction.kind === 'approval'` 映射为 `pending_approval`；`question` / `plan-review` 不接入、不显示，留待下一迭代评审。

**理由**：
- M0 §6 的最小事件集只有 `session.tool.pending_approval`，question/plan-review 属于范围扩展；
- DSH 只暴露最高优先级的 pendingInteraction，插件无法可靠同时看到 approval 和被遮蔽的 question；
- 当前目标是收口 M1/M3 和发版，不在发版前扩大阻塞交互范围。

**影响面**：`pendingKind` 仍只有 `approval`；不新增状态/信号；`docs/m3-implementation` 的 D28 待办保留。

**后续**：如果产品负责人要求纳入，需单独立项，验证 question/plan 的 key、优先级和与 approval 遮蔽的共存场景。
