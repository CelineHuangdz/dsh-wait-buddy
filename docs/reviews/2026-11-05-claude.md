# DSH 插件 dsh-wait-buddy（v0.3.0）评审报告

## 前置总览

- **总体结论**：基本达标，但核心风险没有收口。Host 投影、只读、不反向控制这几条守住了；单向联动和审批对游戏的影响规则还没实现（仓库自述只完成到 M1+M2，联动是 M3）。另外，Agent 的提问（question）和计划评审（plan-review）这两类阻塞请求在面板上完全看不到。
- **核心风险**：用户正在玩游戏时，Agent 卡在审批、提问或计划评审上，面板仍显示"正在执行任务"，游戏也继续跑。这正是"不能错过审批提醒"这个痛点的反面。
- **底座演进潜力**：中等。Host 投影这一层（从会话日志纯函数折叠出状态，只读）是好底座，统计、回放这类需求都能低成本从日志推导。最大的架构瓶颈在 Client 侧：根本没有"信号层"，只有电平式快照（level-triggered）。再加上单个 1600 行文件、模块级单例、游戏模式写死成三元表达式，联动规则、多游戏、多实例三条演进线都会撞到这里。

**依据说明**：工作区里没有 M0 基线原文，README 和 decisions 只以"M0 §2/§5/§6/§10/§11"的形式引用它。下文的基线比对依据是你给的需求描述、仓库文档，以及 `node_modules/@deepseek-ai/*` 里的 DSH 契约（类型声明和实现）。标注"待基线确认"的条目需要你用原文核对。

## 1. 业务与需求匹配度

**1.1 🔴 提问和计划评审类的阻塞请求不可见；审批被更高优先级的请求遮蔽时也会丢失**

- **现象**：`compose()` 只认 `pendingInteraction.kind === 'approval'`。而 DSH 的 `SessionStatus.pendingInteraction` 只暴露最高优先级的那一条请求。优先级分别是：审批 `0`（`dsh-client-ui-approval` 里 `registerPendingInteraction(() => 0)`），提问 `1`、计划评审 `2`（`ui-user-questions` 里 `kind === "plan-review" ? 2 : 1`）。

```204:236:dsh-wait-buddy/client.js
      const compose = () => {
        ...
        const pending = status === undefined ? undefined : status.pendingInteraction
        const approval =
          pending !== undefined && pending !== null && pending.kind === 'approval'
            ? pending
            : undefined
```

- **风险**：Agent 调用 ask_user 或进入计划评审时，同样在阻塞等人，但面板显示"正在执行任务"，进度条还在动。审批和提问同时存在时，审批也会被遮蔽。这是错过关键交互的直接来源。
- **方案**：只要 `pendingInteraction` 非空，就统一进入 `awaiting_user` 告警态，再按 `kind` 分文案：审批显示工具名，提问显示"Agent 在等你回答"，计划评审显示"等待确认计划"。未知 kind 走兜底文案"Agent 正在等待你处理"。状态名建议从 `pending_approval` 泛化为 `awaiting_user`，`kind` 作为子字段。

**1.2 🔴 审批弹窗对游戏的影响规则缺失（基线约定）**

- **现象**：README 明说"等待审批不会暂停游戏（那是 M3）"。代码里游戏区不读取任何监控状态。
- **风险**：贪吃蛇是实时游戏，用户视线集中在画布上。审批到来时游戏不停，提示又在顶部，最容易漏看。这是本插件第一优先级的风险。
- **方案对比**：
  - **方案 A：审批进入时自动暂停，审批消失时自动恢复。** 优点是零操作。缺点是用户可能还没看清就被拉回游戏；连续审批时会频繁暂停、恢复，体验抖动。
  - **方案 B（推荐）：审批进入时自动暂停，棋盘上叠一层"Agent 等待审批，请在下方处理"；审批消失后叠层改为"已处理，按空格或点击继续"，由用户手动恢复。** 优点是不会悄悄恢复，连续审批天然防抖。缺点是多一次操作。
  - 五子棋是回合制，不需要暂停，只叠提示层、不锁盘。

**1.3 🔴 未知的 `turn/end` 结束原因会被显示为"任务执行成功 ✅"**

- **现象**：DSH 类型注释写明 `TurnEndReasonMap` 是 "Merge-extensible sum type"，其他插件可以合并新的结束原因。但 `endedWith` 的 `default` 分支和 `completed` 合在一起，都映射成 success。

```174:178:dsh-wait-buddy/index.js
    case 'forked':
      return { status: 'idle', errorMessage: '' }
    case 'completed':
    default:
      return { status: 'success', errorMessage: '' }
```

- **风险**：DSH 或其他插件一旦新增结束原因，比如 goal 预算耗尽，就会被误报为成功。这属于假阳性的成功提示，违反"不做假状态"原则。
- **方案**：`default` 映射到一个新的中性终态 `ended`，文案"本轮已结束"，`errorMessage` 带上 `reason.kind`。同时把 `stateVersion` 升到 3。

**1.4 🔴（待基线确认）会话切换和任务启动时，游戏状态不重置**

- **现象**：监控侧在 `turn/start` 时会清空 `stepCount` 和活动流，这一点与基线一致。但游戏是模块级单局：切会话、新任务启动都只暂停、不重置（README 写的是"模块级单局"）。
- **风险**：如果 M0 原文要求"会话切换/任务启动时重置"，这就是未登记的基线偏离。现在 decisions 里没有对应条目，也违背了项目自定的"先文档后代码"规则。
- **方案对比**：
  - **方案 A：维持全局一局。** 理由是游戏属于用户，不属于会话。必须补一条决策记录，显式修订基线。
  - **方案 B：按会话各存一局（以 sessionId 为键的 Map）。** 语义最清晰，但多会话来回切时，用户会困惑"我刚才那局去哪了"。
  - **方案 C：切会话时重置。** 最贴近基线字面要求，但伤害玩家体验。
  - **推荐 A，并补决策记录。** 前提是你确认 M0 原文允许修订；如果不允许，选 C。

**1.5 🟡 范围投入倒挂：基线外的功能做了，基线内的联动没做**

- **现象**：五子棋及三档 AI 难度（D16）、速度和难度设置与持久化（D17），都来自 M0 §10 的 M4 备选池。而 M3 的单向联动，包括审批暂停，一行都没有。代码量上，游戏约 1000 行，监控约 300 行。
- **风险**：插件定位是"监控为主、游戏为辅"，实际投入比例正好相反。
- **方案**：冻结游戏玩法类需求，下一迭代全部投到信号层和联动（见第 4 节）。

**1.6 🟡 活动流引入了基线外的事件 `assistant/message`（D9）**

- **现象**：README 的铁律第 3 条写"不订阅基线之外的事件"，D9 又以产品负责人要求为由加了 `assistant/message`。文档自相矛盾，模型推理内容会出现在面板上。
- **风险**：录屏或投屏时泄露推理内容；铁律失去约束力。
- **方案**：把铁律第 3 条改成"例外须在 decisions 中登记"。另外提供一个"显示思考摘要"开关，默认开启但可关闭。

**1.7 🟡 价值判断：缺少"等了多久"和"是不是卡住了"这两个关键信息**

- **现象**：面板只显示"更新于 HH:MM:SS"这个绝对时间，没有"本轮已运行 mm:ss"，也没有"距最近活动 N 分钟"。
- **风险**：Agent 长时间空闲，或某个工具执行了 20 分钟时，用户分不清是在正常工作还是已经卡死。这恰好是等待场景里最需要回答的问题。
- **方案**：投影增加 `startedAt`，在 `turn/start` 时写入。Client 每秒渲染一次相对时间，用独立的轻量计时器，不触发投影更新。超过阈值（可配置，比如 5 分钟）没有新活动时，状态行追加弱提示"已 N 分钟无新活动"，只做提示、不告警。

## 2. 使用体验

**2.1 🔴 视觉重心被游戏抢走**

- **现象**：棋盘是整屏唯一的深色实体块（硬编码 `#0d1624`），蛇是高饱和薄荷绿 `#8ef7b0`。告警条只有 12% 混色背景加 1px 描边。游戏得分文字是 15px，和状态文案同号；游戏按钮 14px，反而比监控元信息（11px）大。
- **风险**：在亮色主题下反差更明显，注意力会持续停在游戏上。
- **方案**：
  1. 告警态下给游戏画布加 60% 遮罩并去饱和（这是游戏消费信号的方式，不影响监控）。
  2. 游戏说明行降到 12–13px，次级色。
  3. 棋盘配色跟随主题令牌，或者至少降低饱和度。

**2.2 🔴 告警条不是吸顶的，与 ui-spec 自相矛盾**

- **现象**：ui-spec 写"告警永远在最上方，且不依赖滚动可见"。但 `.wb-root` 是 `overflow:auto`，`.wb-alert` 处在普通文档流里，没有 `position:sticky`。棋盘最小高度 200px，加上状态区和说明行，矮窗口里一定会出现滚动。
- **风险**：用户滚到棋盘区域后，告警出现在视口之外。
- **方案**：给告警条加 `position:sticky; top:0; z-index:1`，背景用不透明的 `bg-base`。

**2.3 🟡 贪吃蛇连按方向键会自杀，连按还会冻结蛇的移动**

- **现象一**：只缓存一个 `nextDir`。向右走时在一个 tick 内快速按"上、左"，"左"会覆盖"上"，下一帧直接掉头撞自己，游戏结束。
- **现象二**：每次 `set()` 都会调用 `schedule()`，先清掉再重建 `setInterval`。所以每次有效按键都会把下一个 tick 往后推，连续按键时蛇停住不动。

```436:441:dsh-wait-buddy/client.js
    function turnGame(state, dir) {
      if (state.status !== 'running') return state
      const current = state.nextDir === null ? state.dir : state.nextDir
      if (dir === current || dir === OPPOSITE[current]) return state
      return { ...state, nextDir: dir }
    }
```

- **方案**：
  1. 方向改成最长 2 的队列，每次入队时和队尾方向比较是否反向。
  2. `schedule()` 只在 `status` 或 `tickMs` 变化时重建计时器。

**2.4 🟡 任务成功没有任何"到达感"**

- **现象**：失败有横幅，成功只是状态文字变绿。
- **风险**：任务完成是用户最想第一时间知道的事件，但玩游戏时注意不到。
- **方案**：成功时在棋盘角落出一个 3 秒自动消失的非模态提示"本轮已完成 · 查看对话"，不暂停游戏。这比失败横幅弱一档，符合"醒目但不扰民"。

**2.5 🟡 文案与实际不符**

- `game.startBody` 写"方向键或软按钮控制"，但软按钮已被 D7 移除。
- `locale/zh.json` 的描述写"已完成步数"，但界面已不显示步数（D9）。
- "任务执行成功 ✅"对应的 `completed` 只代表本轮正常结束，不代表任务目标达成。建议改成"本轮已完成"。
- 告警条和状态行重复显示"【重要】……！"；方括号加感叹号显得粗糙，建议保留告警条，状态行简化为"等待审批"。

**2.6 🟢 方向键需要先聚焦视图**

- 方向键要求焦点在视图内。这是正确的取舍，不会抢输入框的按键。另外核实过：DSH 原生审批面板的 Enter/Esc 快捷键只在焦点位于面板内时生效，所以玩游戏时不会误批。
- 但首次进入视图时焦点不在根节点，用户必须先点一下。建议进入视图时，如果当前焦点不在输入框里，就自动聚焦根节点。

## 3. 页面布局与 UI 结构

**3.1 🟡 信息层级倒置**

| 层级 | 应包含的内容 | 现状 |
|---|---|---|
| 核心 | 状态、等待用户处理、已运行时长 | 状态 15px；没有时长 |
| 次要 | 活动流、更新时间 | 活动流 12px，合理 |
| 装饰 | 免责说明、游戏得分 | 免责说明 10px 常驻；得分 15px 偏大 |

- **方案**：免责说明挪进 tooltip，或者只在首次显示；得分降级到 12px；状态区加入时长。

**3.2 🟡 窄窗口适配**

- **现象**：`.wb-alertTitle` 设了 `white-space:nowrap; flex:none`，宽度小于约 320px 时会撑出横向滚动。`.wb-status` 的 `min-width:260px` 加上 24px 内边距，大约 310px 以下会溢出。说明行在窄窗口里会折成 3 行以上，进一步挤压棋盘。
- **方案**：告警标题允许换行；状态列 `min-width` 改为 `min(260px,100%)`。视图宽度小于 480px 时，用 container query 隐藏游戏设置分组，只保留切换和暂停。视图高度小于 360px 时，游戏区整体折叠成一行"游戏已折叠"，保证监控区不被挤压。

**3.3 🟢 动效**

- 运行态的扫光条 `wb-sweep` 无限循环，没有适配 `prefers-reduced-motion`。建议补上；运行中可以只保留状态点呼吸效果。

**3.4 🟢 浅色主题**

- 棋盘、浮层、主按钮都是硬编码的深色配色，在浅色主题里是一个突兀的黑块。可以先接受，M1 再接主题令牌。

## 4. 数据联动与事件订阅架构（重点）

**4.1 🔴 "信号层"实际上不存在，解耦是因为功能缺席，而不是设计出来的**

- **现象**：`createMonitorSource` 只产出电平式快照，没有边沿事件，例如"进入审批""本轮结束"。游戏和监控之所以解耦，只是因为两边互不读取。
- **风险**：M3 一旦开始做，最自然的写法是在 `GameArea` 里直接读 `useMonitorState`，然后写 `if (status === ...)`。这会立刻造成强耦合，而且会把切会话时的投影基线误判成"刚发生的事件"。
- **方案（必须先于任何联动功能落地）**：

```javascript
// 信号契约（只读，游戏只能消费）
// { type: 'task.start'|'task.end'|'step'|'await.enter'|'await.exit',
//   sessionId, key, at, detail }  key 用于去重：await 用 pendingInteraction.key，task 用 `${turn}`
```

  1. 从相邻两个快照的差分推导边沿。
  2. 规则一：挂载或切会话后的第一个快照只作为基线，不发出任何信号。
  3. 规则二：同一个 `key` 只发一次。
  4. 规则三：`at` 早于挂载时间的事件丢弃，防止回放刷奖励。

- **实现方式对比**：
  - **方案 A：模块内的轻量 `EventTarget`。** 成本最低，适合 M0/M1。
  - **方案 B：注册成 Cordis Client 服务（如 `waitBuddySignals`），供第三方游戏插件订阅。** 适合 M2。
  - **推荐先 A 后 B**，契约从一开始就按 B 的形态定义。

**4.2 🔴 绕过了 DSH 公开的标准 Hook，`uiSession` 依赖也没有声明**

- **现象一**：`conversation.view` 处于 session 作用域，标准 props 里已经提供 `useProjection`、`useSession`，全局还有 `useSessionStatus`（见 `dsh-client-ui-session` 的 `SessionStandardProps` / `GlobalStandardProps`）。插件却走了内部对象链：`ctx.sessions.binding(id).session.projections.faceOf()`、`refreshProjections()`。
- **现象二**：`uiSession` 用 `ctx.get('uiSession')` 临时读取，没有写进 `inject`。DSH 自带的插件开发规范（`practices.md`）明确要求可选服务要放进 `inject` 或用 `ctx.inject()` 声明。

```262:276:dsh-wait-buddy/client.js
      const start = () => {
        ensureProjection()
        const disposersNext = []
        const binding = bindingOf()
        if (binding !== undefined) {
          ...
        }
        const uiSession = ctx.get('uiSession')
        if (uiSession !== undefined && uiSession.sessionStatus !== undefined) {
```

- **风险**：
  1. `uiSession` 如果比本插件晚加载或被重载，审批信号会静默失效，界面上没有任何提示。
  2. 挂载时如果 `binding` 还是 `undefined`，之后不会重新订阅，活动流就冻结了；状态只在 `sessionStatus` 变化时才被顺带刷新。
  3. 内部对象链是 DSH 升级时最先变动的部分。
- **方案对比**：
  - **方案 A：保留现有路径，补"binding 出现后重新订阅"，并声明 `inject: { optional: ['uiSession'] }`。** 改动小，但升级风险仍在。
  - **方案 B（推荐）：改用 `props.useProjection('waitbuddy')` 和 `props.useSessionStatus(m => m.get(props.sessionId))`。** 订阅生命周期交给 DSH，`createMonitorSource` 可以删掉大约 120 行。

**4.3 🟡 Agent 异常断开时会永远停在"运行中"**

- **现象**：`compose()` 只在投影是 idle 时才参考 `running === true`。如果投影显示 `running` 而 `sessionStatus.running === false`（Host 断开、进程崩溃，此时还没有冷读补写 `interrupted`），面板会一直显示"正在执行任务"加扫光条。另外，`ready` 字段算出来了，但没有任何地方使用。
- **方案**：
  1. 投影是 `running`、`running === false`、并且持续超过 5 秒宽限期时，显示"状态同步中断（可能已断开）"。
  2. `ready === false` 时显示"监控数据未就绪（Host 半未加载？）"，不要显示"空闲"。

**4.4 🟡 子 Agent 的审批和提问可能不会冒泡到父会话（需要实测）**

- **现象**：WaitBuddy 只看当前 `sessionId`。子 Agent 是独立的子会话；工作区树里有 `runningSubagentCount`，但父会话的 `pendingInteraction` 是否包含子会话的请求，我在类型里没找到依据。
- **方案**：先用测试用例 TC-11（见下文测试清单）实测。如果不冒泡，至少在面板上显示"子 Agent 运行中 N 个"，并提示去对应会话处理。

**4.5 🟡 多轮目标（goal continuation）会造成"成功"闪烁**

- **现象**：DSH 的 `user/message` 包含"entered goal continuation round"，也就是目标续跑时每一轮都是新的 turn。每轮结束都会短暂显示"任务执行成功 ✅"，然后活动流被清空。
- **方案**：短期内终态加 1.5 秒防抖：如果期间又收到 `turn/start`，就不显示成功。M1 再基于 goal 投影识别"整个目标是否完成"。

**4.6 🟢 每个 step 都触发一次无效的重渲染**

- **现象**：`stepCount` 不显示，但每次 `step/end` 都会让 `revision` 加一，推送一帧投影，进而让整个视图（包括没有 memo 的 `GameArea`）重渲染。
- **方案**：`GameArea` 用 `React.memo` 包起来。是否保留 `stepCount` 等 M1 联动方案定了再决定，届时可以改成只在信号层里计数。

**4.7 🟢 推理摘要截取的位置**

- `reasoningOf` 截取的是最后一个推理块的开头 120 个字符，往往是"The user wants…"这种开场白。改成取最后一句或末尾 120 个字符，信息量更高。

## 5. 代码与插件工程质量

**5.1 🟡 多实例冲突：模块级单例**

- **现象**：`gameCanvas`、`boardEl`、`rootEl` 都是模块级变量，注释写着"同一时刻只渲染一个"。但 conversation 有主视图和嵌入视图两种出现方式，DSH README 有说明。两个 WaitBuddy 视图同时挂载时，后挂载的会覆盖引用；任何一个卸载都会把引用置为 `null`，剩下的那个视图就不再绘制，焦点回归也失效。
- **方案**：引用改成组件内的 `useRef`。`gameStore` 是否全局共享取决于 1.4 的决定；即使共享，绘制也要按实例分开。

**5.2 🟡 插件重载后状态不对**

- **现象**：`gameStore` 在模块工厂里创建，而不是在 `apply` 里。如果 `slots`、`sessions` 或 `locale` 重载导致插件 fiber 重启，第一次 dispose 时 `visibilitychange` 监听已经被移除，第二次 `apply` 继续复用这个"已销毁"的 store，于是页面隐藏时自动暂停失效。`clientCtx` 和 `boundT` 也是模块级的，可能残留旧的 ctx。
- **方案**：所有 store 都在 `apply(ctx)` 里创建，通过闭包或 React Context 传给视图。

**5.3 🟡 没有错误边界**

- **现象**：游戏绘制或状态机抛出异常时，会连同监控区一起崩掉，DSH 的槽位渲染器是否兜底不确定。
- **方案**：监控区和游戏区各包一个错误边界。游戏崩溃只替换游戏区为"游戏出错，点击重置"，监控区不受影响。这一条直接关系到"监控优先级高于游戏"。

**5.4 🟡 文档与代码漂移**

- **现象**：项目自定"先文档后代码"，但目前存在多处不一致：
  - ui-spec §1 写棋盘高度 `min(40vh,360px)`，§2 和代码都是 `min(46vh,480px)`。
  - README 结构说明里还有"软按钮"。
  - D16 写"不引入设置项"，被 D17 推翻却没有标注已推翻。
  - ui-spec §6.2 写"重新开始"，代码里是"重置"。
  - 代码注释有重复（第 130 行、第 1400 行），并且残留"M1: monitoring only, no game"。
- **方案**：加一个 CI 脚本：抽取文案键与 ui-spec 表格比对。decisions 被推翻时统一加"已被 Dxx 取代"标注。

**5.5 🟡 可测试性**

- **现象**：导出了 `__game`，注释写"供单测使用"，但仓库里没有任何测试，Host 的 `fold` 也没有测试。
- **方案**：给 `fold` 加表驱动测试，覆盖每一种 `turn/end` 结束原因、`turn` 不匹配、重复的 `turn/start`；给 `tickGame`/`turnGame` 加测试，包括 2.3 的掉头自杀回归。用 `node --test` 即可，不需要引入框架。

**5.6 🟢 生命周期清理**

- `ResizeObserver` 会断开，监控订阅会退订，计时器在 dispose 时会清理，这部分合格。
- 小瑕疵：`visibilitychange` 监听在模块执行时就注册了；如果插件被禁用但模块已加载，这个监听会残留。

**5.7 🟢 性能**

- 贪吃蛇每个 tick 只重绘自己的 canvas，网格点最多约 3000 次 `fillRect`；页面隐藏或视图卸载时会暂停。五子棋 AI 是同步计算，候选点不超过 225 个，耗时可忽略。不构成拖累 DSH 主程序的风险。
- Host 投影对所有会话都会计算并推送（即使从没打开过 WaitBuddy），单次开销很小，但会进入每个会话的 checkpoint。可以接受，建议写进 README。

## 6. 底座可扩展能力与长期演进

**6.1 扩展成本分级**

| 演进方向 | 成本 | 理由 |
|---|---|---|
| 单会话等待时长、步数、工具次数统计 | 低 | Host 投影是对日志的纯折叠，加字段即可，历史会话也能追溯计算 |
| 等待日志导出 | 低到中 | 新增一个有长度上限的投影（每轮摘要列表） |
| 新增小游戏 | 中 | `GameArea` 里有 4 处以上 `mode === 'snake' ? … : …`，需要先抽象游戏适配器 |
| 自定义信号到游戏的映射规则 | 高 | 依赖信号层（目前不存在）和一张声明式规则表 |
| 多任务对比监控、跨会话统计 | 高 | 当前绑定单个 `sessionId`；跨会话需要会话列表投影或存储服务 |
| 历史任务回放 | 中到高 | 日志可重放，但需要独立的时间轴 UI，不适合放在等待面板里 |
| 审批融入游戏关卡 | 中（前提是信号层就绪） | 见 6.4 |

**6.2 🟡 硬编码和强绑定清单**

- 游戏模式、设置分组、文案键都按两款游戏写死。
- 速度和难度预设是常量。
- 投影 key `'waitbuddy'` 散落在两个文件里。
- 告警态的判断写死在 `compose()` 里。

建议抽出下面这个适配器接口：

```javascript
// GameAdapter：新增游戏只需注册一个对象
// { id, titleKey, settings?: { key, options }, Board: Component,
//   pause(), resume(), reset(), onSignal?(signal) /* 只改游戏内状态 */ }
```

**6.3 分层边界建议**

- **底座加固层**：投影、信号层、生命周期、错误边界、兼容性检测。只有这一层可以读取 DSH 的 API。
- **玩法扩展层**：游戏适配器和联动规则。只能消费信号，不能 import DSH 的任何东西。
- **用户自定义层**：配置面板、映射规则开关。只能修改玩法层的参数，不能改信号定义。
- 目前三层混在同一个文件、同一个闭包里，边界并不存在。

**6.4 🔵 远期想法："审批作为关卡解锁"**

- **可行的形态**：用户在原生面板里处理完审批（信号层收到 `await.exit`）后，解锁一个皮肤或奖励关。这是纯事后奖励。
- **禁止的形态**：
  - 在游戏里放"批准"按钮；
  - 用"通关才能处理审批"来延迟审批；
  - 根据游戏状态自动批准或拒绝。
- **风险**：奖励机制可能诱导用户为了解锁而草率批准。建议奖励只与"响应时长"挂钩，不与"批准还是拒绝"挂钩。

**6.5 依赖风险清单**

| 依赖 | 稳定性 | 预案 |
|---|---|---|
| `conversation.view` 槽、`openView` | 公开契约，稳定 | 保留 |
| `useProjection`、`useSessionStatus` 标准 props | 公开 | 迁移到这里（4.2） |
| `ctx.sessions.binding().session.projections`、`refreshProjections` | 内部对象链，高风险 | 移除 |
| `PendingApproval.toolName`、`kind` 字段 | 类型公开，可通过声明合并扩展 | 只读 `kind` 和 `key`；`toolName` 缺失时降级 |
| `TurnEndReason` | 明确是可扩展的 | 修复 default 分支（1.3） |
| `window.__ModuleLoader__`、`--dsw-alias-*` 主题令牌 | 半内部 | 令牌缺失时用 CSS 兜底值 |
| `zod@4.4.3` 精确锁版本 | 未验证 DSH 投影注册对 zod 版本的要求 | 确认 DSH 是否只要求 Standard Schema |
| 只在 DSH `0.2.1-rc.5` 上测试过，没有 `peerDependencies` 或 `engines` 声明 | 升级时无防护 | 加 `peerDependencies` 范围，再加运行时能力检测横幅（"当前 DSH 版本缺少 X，部分提醒不可用"） |

## 演进路线规划

**M0 补丁（1 个迭代）：止血，守住"不漏审批"**

- **目标**：做完第 1、2、4 节中所有 🔴 条目，外加 4.3、5.3。
- **前置条件**：拿到 M0 原文，确认 1.4 的方向；决策记录先行。
- **风险**：迁移到标准 Hook（4.2 方案 B）会改动数据通路，必须用 TC-05、TC-08、TC-14 回归。
- **取舍**：不新增任何游戏和玩法；信号层只实现 `await.enter/exit` 和 `task.start/end` 四种信号，其中只有"审批暂停"一个消费者。

**M1 能力扩展（2–3 个迭代）**

- **目标**：信号层契约冻结；游戏适配器重构；联动规则 v1（完成 +N 分、step 加速等，硬编码但集中在一张规则表里）；等待时长和单会话统计投影；监控与游戏分区错误边界；主题令牌化。
- **前置条件**：M0 的信号契约已稳定，单测覆盖 `fold` 和信号差分。
- **风险**：奖励机制会提升游戏的吸引力，与"监控优先"冲突。每条规则都要回答一个问题："它会不会让用户更晚发现审批？"
- **取舍**：多任务对比监控不进 M1，那需要跨会话数据源，是另一个产品形态。

**M2 自定义生态**

- **目标**：信号层注册为 Cordis 服务（4.1 方案 B），让第三方游戏插件能接入；映射规则做成用户可配置项，用插件 Config 或界面 + localStorage 存储；等待日志导出；"审批后解锁"奖励。
- **前置条件**：M1 的分层边界落地，玩法层零 DSH 依赖。
- **风险**：第三方游戏插件可能绕过信号层直接读 DSH。只能靠审查和规范约束，没有技术手段强制，因为 Cordis 没有沙箱。
- **取舍**：历史回放建议独立成单独的视图或插件，不要塞进 WaitBuddy。

## 绝对不能做的改动（基线红线）

1. 游戏或插件内任何地方，都不能调用审批应答、取消、重试、发送消息、修改目标等写操作。D14 的"查看对话"只做视图导航，是允许的上限。
2. 不能替换或隐藏 `conversation.composer` 或 `conversation.composer.bar`（D2），原生审批面板就渲染在这里。
3. 不能让游戏状态影响告警的显示：不能"游戏进行中延迟提醒"，不能"通关才显示审批"。
4. 不能往会话日志里追加新类型的事件；状态只能从现有事件派生（DSH 规范明确禁止追加，否则会话将无法重新打开）。
5. 不能为了让游戏遮罩显得醒目而抢走焦点：审批出现时，焦点留在用户原来的位置，由原生面板自己负责交互。
6. 不能伪造进度百分比或总步数（M0 §2、D1）。

## 推荐优先落地的 M0 迭代清单（按顺序）

1. 告警态从"只认审批"泛化为"所有待处理交互"（1.1）。
2. `turn/end` 的 default 分支不再映射成成功，`stateVersion` 升到 3（1.3）。
3. 改用 `useProjection` 和 `useSessionStatus`，并声明 `uiSession` 依赖（4.2）。
4. 最小信号层，加上"审批时暂停并叠层、手动恢复"（4.1 + 1.2 方案 B）。
5. 告警条吸顶，告警态下给游戏加遮罩（2.1、2.2）。
6. 断开、未就绪时的降级展示（4.3）。
7. 监控和游戏分区错误边界（5.3）；修复多实例的模块级引用（5.1）。
8. 贪吃蛇方向队列和计时器修复（2.3）。
9. 补决策记录：会话切换时游戏如何处理（1.4）、活动流事件例外（1.6）；同步修正文档漂移（5.4）。
