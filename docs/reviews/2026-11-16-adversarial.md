# WaitBuddy 0.12.0 对抗性评审（2026-11-16）

**评审对象**：`index.js`（评审时 279 行 Host 侧）+ `client.js`（评审时 5660 行、245KB Client 侧）+ 变更日志 12 个版本。
**总体判断**：工程纪律好于 95% 的社区插件（纯函数 fold、错误边界、确定性测试、双语词典），但**产品定位已经失焦，且与宿主的耦合方式正在积累技术债**。以下按严重度排列。

---

## 一、产品维度：监控器变成了游戏机 —— 严重的范围失控

**指控**：插件自述是 *"monitors long-running Agent tasks, with approval/failure alerts"*，但看代码构成：抓精灵（safari）相关代码约从 3200 行铺到 4500+ 行，加上像素绘制管线、值噪声地形、54 种精灵烘焙、四主题色板——**游戏代码占 client.js 的 60% 以上，监控本体（fold + FeedRow + ActivityPulse + 通知）不足 15%**。

变更日志是铁证：0.10 → 0.12 两个版本、四天时间，**全部条目都是游戏美术和按键修复**，监控看板本身唯一的改进是“活动流折叠 ×N”和“脉冲条”。用户在等任务时最需要什么？——预计剩余时间、token 消耗、失败历史聚类、多会话总览。这些一个都没有。`stepCount` 只是个递增计数器，`activity` 只留 3 条（`ACTIVITY_LIMIT = 3`，index.js:42），连“这个会话过去一小时干了什么”都回答不了。

**改进建议**：
1. **把游戏拆成独立插件**（`dsh-wait-buddy-games`）或运行时可选模块。理由：不玩游戏的用户被迫为 245KB 立即加载的 client 买单；游戏与监控的迭代节奏完全不同频，捆在一起让每次“修精灵”都要重发“监控器”。
2. 监控侧补齐真正的等待者诉求：**turn 时长统计、活动流环形历史（哪怕 50 条）、按会话聚合的失败率、审批等待时长分布**。这些数据 fold() 里现成都有。

---

## 二、架构维度：与宿主的耦合是“DOM 念力”，脆弱且不可持续

这是全插件最危险的部分。看 `openFullView()`（client.js:4989-5021）：

```js
const tabs = Array.from(document.querySelectorAll('[role="tab"]'))
return tabs.find((el) => (el.textContent || '').trim().startsWith('WaitBuddy'))
...
label.includes('更多会话视图') || label.includes('session views')
await new Promise((resolve) => setTimeout(resolve, 120))  // 等菜单弹出的魔法延时
```

四个问题，每一个都是定时炸弹：

1. **靠界面文案匹配 DOM**。`startsWith('WaitBuddy')`——宿主哪天给 tab 加个图标前缀、改个本地化文案，静默失效。更实锤的 bug：`'更多会话视图'` 硬编码了**中文和英文**两个字符串，宿主界面切到日语/德语时这个 fallback 直接死亡。这是已经埋着的缺陷，不是假设。
2. **120ms `setTimeout` 等菜单渲染**——竞态窗口。慢机器上菜单还没挂载，`querySelectorAll` 扑空，返回 false。
3. 合成 `wheel` 事件（client.js:5464）——为了骗过宿主的“跟随尾巴动画”，向 `document` 派发假滚轮。**任何其他插件或宿主自身的 wheel 监听都会收到这个伪造事件**。一个插件污染全局事件流来解决自己的问题，这是典型的“我修我的 bug，别人接我的锅”。
4. 祖先滚动容器重置（client.js:5481-5491）靠 `depth < 6` 逐层 `getComputedStyle` 猜哪层是滚动容器——宿主改一层 DOM 嵌套就失效。

**空格键战争史**（变更日志 0.11.0 自己写的四轮 escalation）值得单独批判：React onKeyDown → window 冒泡 → window 捕获 → `stopImmediatePropagation` → 合成 wheel → 最终**投降改键 F/Q**。这条轨迹说明插件在用越来越暴力的手段与宿主打按键争夺战，而 `stopImmediatePropagation`（client.js:5456）会掐断**同节点上所有其他监听者**——包括无辜的第三方插件。

**改进建议**：
1. **向宿主要公开 API**：`openView(viewId)`、`isViewActive(viewId)`、`consumeKeys(scoped)`。变更日志显示作者已经逆向读懂了宿主源码（跟随尾巴、快照机制），说明有能力提 PR——**修宿主比对抗宿主便宜**，四轮按键战争消耗的时间足够提三个上游 PR。
2. 在 API 到位前，所有 DOM 念力加**能力探测 + 版本指纹**：启动时探测一次，失败则永久降级为“请手动点击”，并在看板显示“宿主适配层：降级”。现在 `openFullView` 返回 false 只弹 4 秒 toast，用户根本不知道是插件坏了还是自己操作错了。
3. 文案匹配至少改成 `aria-label` / `data-*` 属性匹配，并把 locale 字符串表化——硬编码中文是最先该修的。

## 三、正确性维度：fold() 干净，但状态语义有暗坑

先给赞美：`fold()`（index.js:210-261）是纯函数、不可变更新、`WeakMap` 缓存视图、旧 turn 的迟到事件有防护——这是教科书级的投影实现。但：

1. **`unknown → aborted` 映射是在骗用户**（D22 决策，endedWith，index.js:187-196）。宿主出现未知终态原因时，用户看到“已中断”——他会以为是自己的操作或网络导致的可重试中断，实际上可能是任何未分类错误。**错误状态被伪装成用户熟悉的状态，比显示“未知”更危险**。理由：用户对“已中断”有既定响应动作（重发），对未知终态应该先看日志。
2. **`forked → idle` 丢信息**（index.js:184）。会话被 fork 后监控静默归零，没有任何“这个会话已分叉”的痕迹。
3. `belongsToTurn` 对 `turn` 缺失的事件**照单全收**（index.js:200-203）——注释说是前向兼容，但意味着一个 malformed 事件可以污染当前 turn 的活动流。既然有 zod，为什么不 `parse` 事件？
4. `stateVersion` 4→5→6 三次连跳，每次都让旧投影缓存失效重算——短迭代期可以接受，但这暗示**投影 schema 演进没有加版本迁移测试**。

**改进建议**：给 STATUS 加 `unknown` 值（UI 显示“未知终态 + 原始原因”）；`forked` 至少在活动流留一条记录；事件入口用已有的 zod schema 做边界校验——依赖都装了，不用白不用。

## 四、供应链与依赖维度：zod 是杀鸡用牛刀，GitHub 浮动源是裸奔

1. **zod 4.4.3 的唯一用途**是校验自己的两个内部 schema（index.js:46-73）——一个 `typeof` 检查就能搞定的事情，引入了带完整 TS 源码、测试文件、几十个 locale 的巨型包。**运行时 schema 校验对内部数据结构是过度设计**：状态是自己写自己读的，不是外部输入。改进：删掉 zod，手写 30 行断言；或只在测试里用（devDependency）。
2. **`github:CelineHuangdz/dsh-wait-buddy` 浮动源安装**意味着每次更新拉的是 main HEAD——**没有版本锁定、没有签名、没有 provenance**。今天 main 是 0.12.0，明天被 force-push 成恶意代码，`install_bundle` 会照单全收。CHANGELOG 里“37→104 条目”的供应链验证验的是依赖树，**验不了插件自身代码**。改进：发布时打 git tag，安装用 `github:...#v0.12.0` 固定引用；或发布到 npm（作者以“GitHub-only”为由拒绝过——但防回退保护恰恰是 npm 等注册表的核心价值，GitHub tag 同样可达成，至少用 tag）。
3. 细节好评：zod 精确锁版本、无其他运行时依赖。但 `window.__WB_BUILD_ID__`（0.11.0）往全局命名空间塞调试变量——应该挂在 `document.documentElement.dataset` 上。

## 五、测试维度：数量可观，但“对着 mock 测真问题”

119 单测 + 4 视觉用例，数字漂亮，但变更日志反复出现同一个失败模式：

- canvas 背面缓冲 bug（P0）——4 个视觉用例**全部没抓到**；
- `fitBoard` 永久失效——“静态视觉 harness 不跑 effect，抓不到拟合时序问题”（原话）；
- Todo dock 遮挡——**mock 是 38px，真机 150px**，测试绿灯、真机盖住控制行；
- `SfPortrait is not defined` 崩溃——复现工具没走到遇怪分支。

结论：**测试验的是“代码符合我对宿主的想象”，而不是“宿主真的是这样”**。每次真机翻车后补的都是又一个针对性用例，宿主 mock 从未被系统性校正。

**改进建议**：把 `tools/safari-live.mjs` / `view-live.mjs` 这类真实 DOM 复现工具**CI 化**（Playwright 已在 devDependencies 里，工具都写好了，就差接进 pipeline）；宿主 mock 尺寸/行为参数从“拍脑袋常量”改为对真机截图的定期校准。否则测试数量还会继续涨，P0 还会继续漏。

## 六、性能维度：立即加载 245KB，只为一个可能永远不打开的视图

`package.json` 里 `"immediately": true`——client.js（245KB 未压缩源码）在**每次应用启动**时全量解析执行，包含全部三款游戏的绘制代码。用户不玩抓精灵？照样付解析成本。`ActivityPulse` 还有个每 5 秒无条件 `setInterval` 强制重渲染（client.js:5402），哪怕看板不可见。

**改进建议**：游戏代码懒加载（首次切到游戏页签再 `import()`）；脉冲条的 interval 在视图不可见时挂起——插件自己都会监听 `visibilitychange`（client.js:5519），复用即可。

---

## 七、隐私与可访问性：有姿态，不完整

好评：通知文案不含命令/参数（D27）、`prefers-reduced-motion` 已接入（D43/D48）。但：
- 活动流把工具参数（文件路径、shell 命令）明文显示并**一键复制到剪贴板**（FeedRow）——本地单机可接受，但若宿主未来支持 LiveShare/远程查看（DSH 确实有 liveshare 实验插件），这就是敏感数据外泄面。建议复制操作加会话级确认或至少在 README 声明。
- 三款 Canvas 游戏**零屏幕阅读器支持**：棋盘状态、遇怪弹窗对 SR 用户完全不可见。遇怪弹窗有焦点管理（好评）但无 `role="dialog"` 语义。

---

## 八、流程维度：单人高速迭代，决策记录反而成了负债

D1–D48 决策编号、逐条反馈存档、release runbook——流程形式无可挑剔。但反过来看：**0.9.0 的扫雷因“未经产品选型讨论”被整体回退（D46）**，说明“流程”没有真正约束住实现冲动，只是事后提供了回退的纸面理由。四天两个版本、0.10→0.12 全是游戏美术，恰证明决策体系在为错误的方向提供高质量服务。**纪律是手段，不是成就。**

## 优先级排序（若只做三件事）

| # | 改进 | 理由 |
|---|------|------|
| 1 | 游戏拆分为独立插件/懒加载模块 | 止血范围失控 + 245KB 启动成本，一次动作解决两个维度 |
| 2 | 向宿主提 PR 开放 `openView`/按键消费 API，撤除 DOM 念力与合成事件 | 脆弱性的根源；四轮按键战争已证明对抗路线不可持续 |
| 3 | `unknown` 终态独立显示 + locale 硬编码修复 | 前者误导用户决策，后者在非中英文界面已是活 bug |

**一句话总结**：这是一个用造航母的纪律造出来的游乐园——监控核心（fold/projection）值得进官方样例，但它的开发预算正在被像素精灵吃掉，而它与宿主之间那层 DOM 胶水，每一个 `querySelector('[role="tab"]')` 都是在替未来的自己埋雷。

# 总判（第二篇）

0.12.0 的监控底座是认真做的，但产品重心已经倒过来了：最近三个版本主要在给抓精灵打磨像素，并用窗口级键盘劫持去迁就游戏。监控插件正在变成一款会顺便看 Agent 的游戏。

## 1. 产品：游戏吃掉了等待场景

等待 Agent 的人要的是三件事：它还在不在跑、卡在哪、要不要我现在处理。贪吃蛇、五子棋、54 种精灵图鉴回答的是第四件事。

联动只接到贪吃蛇。`signalHub.subscribe` 只调用 `gameStore.handleSignal`（`10-registration.mjs`）。人在五子棋或抓精灵里时，审批仍会暂停，但 step +5 / success +50 发生在另一局、另一块画布上。M3 的“消磨等待”闭环对当前最重的游戏是断的。

全局单局把所有会话的奖励叠到同一条蛇上。离开工位扫一眼“哪些任务还在跑”仍然做不到：胶囊只跟主视图会话。这正是监控产品的主场景，游戏美术不是。

扫雷已经上演过一次：没经选型就做进去，下一版整段删掉（D46）。抓精灵没犯流程错误，但 D48 到 D48e 连续五轮“还是丑”，说明程序化美术的边际收益已经为负。D49 放开“零素材”去嵌 PNG，等于承认这条约束和这个目标互相打架。

建议：冻结新游戏和新美术。下一刀只做监控：多会话迷你列表、工具结果成败、审批仍可被更高优先级交互挡住时的显式降级文案。游戏保持现有三款，不再加区域、物种、难度。

## 2. 宿主集成：插件开始改宿主行为

`WaitBuddyView` 在 `window` 的捕获阶段听 `keydown`，消费后 `stopImmediatePropagation`，再对 `document` 派发合成 `wheel`（`09-components.mjs` 约 767–796 行）。注释写明目的：打断会话的跟随尾巴，免得按游戏键时页面继续被拽到底。

这是在用未公开的宿主内部行为当 API。合成滚轮今天能松开跟随，明天宿主一改条件就会误滚、或把别的插件的滚轮监听打醒。捕获阶段停掉后续监听，也会吃掉同页其它插件对方向键、F、Q、N 的处理。空格键已经换过一轮（空格、F/Q），说明这条路是在和宿主对打，不是在适配契约。

视图跳转同一味道。`openFullView` 用 `[role="tab"]` 的 `textContent.startsWith('WaitBuddy')`，再去全页按钮里找「更多会话视图」（同文件约 316–347 行）。标签一翻译、文案一改、多一个也叫 WaitBuddy 的按钮，跳转就点错或静默失败。D42 加了失败提示，没有去掉这种探测。

布局用 176px 底垫去躲开展开的 Todo dock（D40）。dock 高度是宿主的，写死在插件 CSS 里。dock 再高一截，控制行会再被盖住；dock 收起时，看板会空出一大条。视觉测试按 150px mock 建模，所以这种回归绿灯照样能亮。

建议：游戏键只在棋盘拥有焦点时处理，放弃 window 捕获和合成 wheel。跳转只走已捕获的 `onOpen`；没有就显示“请点 WaitBuddy 标签”，不要扫 DOM。底栏间距改成测量 dock 的真实高度，量不到就用一屏内滚动，不要写死 176px。

## 3. 监控真实性：还剩会误导人的洞

`composeMonitor` 把 durable 投影和进程内 `running` / `pendingInteraction` 合成，未知终态不报成功，这块是对的。剩下的洞会让人做出错误判断。

活动脉冲的注释说能区分“在干活”和“卡住了”。实现只在活动流头部的 `kind:text` 变化时打点（`ActivityPulse`，约 718–727 行）。因此：

- 长时间只有模型推理、没有新的 `tool/call`，条是灭的，人会以为死循环。
- 同一条命令再跑一遍，折叠键不变、文案不变，脉冲也不亮。
- `step/end` 根本不进这条条。步数在涨、脉冲全灭，是这个实现的正常结果。

活动流最多 3 条，而且只记调用、不记结果。`tool/call` 进投影，工具失败、超时、空输出都不进。看板回答的是“刚才喊了什么”，不是“做成了没有”。对排障来说，后者才是等待的人要的。

`status` 在客户端被写成 `pending_approval`，宿主枚举仍是六值。审批一出现，底层的 running / failed 从 `status` 上消失，只留在别的字段里。以后若有代码按六值分支，会把“等待审批的失败轮”看成一种新状态。展示用 `pendingKind` 已经有了，不必再撑破 `status`。

信号去重用一个上限 500 的 `Set`，满了删最旧的键（`02-monitor.mjs` 的 `SIGNAL_SEEN_LIMIT`）。长回合超过 500 个不重复信号后，旧键可以再次加分。这个集合本来是为了防止双视图双倍奖励，淘汰策略把这个保证变成了“只在短回合成立”。

宿主只把优先级最高的一条 `pendingInteraction` 交出来，审批优先级最低。question 或 plan-review 挡在前面时，审批可以存在而插件看不见。代码注释承认了这一点，界面仍把“没有 pending”显示成没有需要人处理的事。这里应该写明“只看到当前最优先的一条阻塞”。

建议：脉冲改记 `revision` 或 `updatedAt` 的变化，推理步也算活动；另外给“距上次工具调用”一个年龄。活动流增加工具结束/失败，至少失败要出现。`pending_approval` 退出 `status`，改由 `pendingKind` 驱动文案。去重改成按 turn 分桶，轮次结束就丢掉该轮的键，不要用全局 FIFO。

## 4. 隐私：命令进了持久投影，复制还在一键之外

D27 正确地拿掉了推理原文。更敏感的是 shell 命令：`fold` 把 `command` 截到 120 字写进投影（`index.js` 的 `toolActivity`）。投影是会话状态，会留在宿主缓存里。`curl`、带 token 的参数、密钥路径，前 120 字就够泄露。

看板每行还有复制按钮，把这段原文送进剪贴板（`09-components.mjs` 约 677 行）。通知路径确实不带命令，但投影和复制路径带。提问类阻塞还会把问题正文截 120 字放进 `pendingDetail`。

建议：投影里只留工具名、参数字段名和路径的 basename；完整命令留在内存态，会话结束即丢。复制前对看起来像密钥的片段打码，或者默认复制工具名，按住修饰键才复制原文。

## 5. 结构：拼接工厂已经超过自己定的阈值

`client.js` 是 `src/client/*.mjs` 按序拼出来的一个工厂函数，片段共享作用域，顺序就是依赖。D38 写的阈值是大约 4500 行或第三款游戏。两件事都已经发生，产物仍然是一份提交进仓库的巨文件。CSS 大字符串住在五子棋片段里。游戏、词典、注册、通知全在同一个闭包。

好处是宿主只加载一个文件，测试能碰到纯函数。代价是：

- 改精灵必须小心不要碰到监控的闭包变量。
- `files` 不包含 `src/`，装出去的人只看得到生成物，和决策文档对不上。
- `stateSchema` 和 `viewSchema` 是两份手写的同一形状，以后加字段很容易只改一边。
- `package.json` 里 `dsh.client.immediately: true`，会话一开就把三款游戏、图集合成、键盘监听都装上，即使用户从不打开这个标签。

建议：保持单文件投递，但片段改成真实模块，由构建脚本打包，禁止跨片段裸引用。监控片段与游戏片段分两个立即加载边界：视图未打开时只保留投影、胶囊和通知。schema 用一份，view 从 state schema 派生。

## 6. 测试：单测很密，契约测试在保护过期文档

119 个单测加 4 个视觉场景，对纯函数是够的。它们保护不了已经出过事故的两类失败：

- 真宿主行为。空格滚动、dock 盖住控制行、插件热更新仍用旧 `client.js` 快照，都是测试全绿之后在真机上发现的。
- 文档契约。`docs/compat.md` 仍写 `stateVersion: 4`、locale 命名空间 `wait-buddy`。代码里版本已是 6，命名空间是 `waitBuddy`（`00-prologue.mjs` 的 `NS`）。这份文件的用途就是新版本 DSH 的核对清单。清单本身是错的，按它验收会放过破坏性升级，也会误报兼容。

视觉 harness 不跑 effect，抓不到 `fitBoard` 那种“测量发生在错误时序就永远巨格”的问题。0.11.0 已经用真实 DOM 复现脚本补过一次，脚本没有进 CI。

建议：把 compat 表生成或断言到源码常量上，版本号、事件名、槽位名对不上就让 CI 失败。把 `safari-live` / `view-live` 收成一条 CI 冒烟。视觉 mock 的 dock、tab 文案、滚动容器跟当前宿主各留一个“故意不一致就红”的探针，避免再按收起态建模。

## 7. 可访问性与注意力

告警吸顶、审批不自动开局，这两点是对的。其余注意力设计偏游戏：

- 脉冲条是 `aria-hidden`，读屏用户得不到“还在不在跑”。
- 抓精灵、贪吃蛇、五子棋的主要操作在 canvas 上，焦点环不完整。D7 已经接受触屏不能玩蛇，0.12 又把抓精灵做成键盘游戏，两套输入假设叠在一起。
- `prefers-reduced-motion` 停了脉冲和水面，棋子移动、寻路、浮字仍在动。
- 浅色主题下游戏区仍是一块深色画布。监控条用了宿主令牌，游戏没有。插件在浅色会话里看起来像嵌进来的另一款应用。

建议：状态行和告警用文本暴露健康度与“距上次活动”，不要只靠颜色和脉冲。游戏动画进同一条 reduced-motion 开关。棋盘边框和说明文字改用 `--dsw-alias-*`，深色只留在格子内部。

## 8. 建议的下一轮，按理由排序

| 顺序 | 改什么 | 理由 |
|---|---|---|
| 1 | 停美术，修脉冲、工具结果、多会话胶囊 | 不修的话，看板会继续对“推理中”和“多任务”说谎，游戏再漂亮也不改变等待决策 |
| 2 | 撤掉 window 捕获和合成 wheel | 这是当前最可能在宿主升级时误伤输入和滚动的行为 |
| 3 | 命令不要进持久投影 | 120 字命令比推理文本更像密钥 |
| 4 | compat 与源码常量锁死 | 现在的兼容流程会按错误清单验收 |
| 5 | 未打开视图时不要加载三款游戏 | `immediately: true` 让每个会话都付抓精灵的成本 |
| 6 | 去重按轮次丢弃，`status` 不再出现第七个值 | 长回合双倍加分、状态枚举被展示字段撑破 |
| 7 | 跳转失败就停在提示，删除 DOM 文案匹配 | 文案耦合比少一个快捷入口更危险 |
| 8 | 游戏联动要么三款都消费同一套暂停/加分，要么文案写明只有贪吃蛇加分 | 现在的奖励发生在用户没在看的那一局里 |

监控半边值得留，而且应该继续作为这个插件的全部理由。游戏已经证明能做成，也证明它会抢走后面每一个版本。下一刀若还是精灵，这个插件的名字就该改成游戏，而不是 WaitBuddy。
