推荐方案 B，并用 pauseReasons: Set<string> 管理暂停原因，禁止审批消失后无条件恢复用户主动暂停的游戏。

🟡 体验缺陷：痛点只解决了一半

🔴 严重问题：双数据源合并存在明显状态优先级错误

【现象】只有 durable 状态为 idle 时，实时 running=true 才覆盖为 running；如果上一轮 durable 为 success/failed，而新任务已开始但投影尚未刷新，页面仍显示旧终态。


【风险】新任务已经运行，页面可能仍显示“任务成功”；相反，实时 running 已变 false 但 durable 仍为 running 时，会长期显示执行中。

【方案】使用显式状态协调矩阵：

approval 存在 → pending_approval；

live running=true + durable 非 running → starting/running-syncing；

live running=false + durable running → settling/stale；

两者一致 → durable 状态；

投影不可用 → degraded，禁止回退成 idle。

【现象】代码维护了 ready，但 UI 完全不读取它；refreshProjections() 失败只写 console。

【风险】监控核心能力不可用时，用户看到的是“空闲 · 等待本会话任务”，这是错误的安全感。

【方案】增加 loading/degraded/ready 数据阶段；失败时显示“监控数据暂不可用，原生审批仍有效”，并提供受控重试。不要无限自动重试。

🔴 严重问题：审批暂停/恢复状态机不存在

【现象】没有审批 key、没有自动暂停来源、没有恢复资格记录。

【风险】直接补一个 status === pending ? pause() : resume() 会导致手动暂停被错误恢复，连续审批也可能提前恢复。

🟡 体验缺陷：隐藏的 stepCount 仍触发全树更新

【现象】每个 step/end 都递增 stepCount、revision 并推送 Client，但 UI 不展示步数，也没有 M3 计分消费。

【风险】高频步骤下会重渲染 WaitBuddyView 和 GameArea，对当前版本没有用户价值。

【方案】M0 阶段停止把隐藏 stepCount 送到 UI；若未来计分需要，用独立 signal 消费，不进入监控渲染快照。

【风险】Agent 断开或投影推送失败时，页面可能永远停留在 running。

【方案】增加 MonitorHealth：

projectionPhase；

lastSignalAt；

sessionOpenState；

lastAgentError；

状态矛盾持续超过宽限期后显示“状态同步异常”，但不要擅自判失败。

🟡 体验缺陷：零自动化测试

【现象】没有 test 文件、test script 或 CI；虽然导出了 __game，但未被测试使用。

【风险】任务状态、审批连续触发、多实例和游戏状态机均只能靠人工验证，升级 DSH 时回归风险高。

【方案】M0 至少补：

Host fold 单测；

Monitor 合并矩阵；

审批 pauseReasons；

Session 切换；

双实例；

游戏状态机；

插件卸载清理；

320px/200% 缩放视觉回归。

🟡 体验缺陷：Client 单文件和模式分支阻碍扩展

【现象】监控、i18n、CSS、贪吃蛇、五子棋、设置和插件注册全部位于一个 1635 行文件；新游戏依赖 mode === 'snake' ? ... : ...。

【风险】增加第三款游戏会扩大条件分支；自定义映射和审批关卡会侵入现有 GameArea。

【方案】拆为：

monitor/projection.js

monitor/source.js

signals/hub.js

games/registry.js

games/snake/*

games/gomoku/*

ui/AttentionRail.js

ui/WaitBuddyView.js

compat/dsh-rc5.js

🟡 体验缺陷：对 RC 版本 API 缺少兼容边界

【现象】发布文档注明只验证 DSH 0.2.1-rc.5，package 没有兼容范围，也没有 capability adapter。

【风险】sessionStatus、投影刷新或 Slot owner props 变化后可能静默失效。

【方案】建立兼容层并做能力探测；维护“DSH 版本 × 插件版本”矩阵。未经多版本验证前，不建议写过宽的 engines.dsh。

🟢 优化改进：发布元数据和文档仍未收口

【现象】release 文档要求 repository/homepage，但 package 未配置；插件元描述仍提“已完成步数”，实际 UI 已删除；README 仍写软按钮和旧棋盘高度。

【风险】影响发布可信度和维护判断，但不直接破坏运行。

【方案】发布前做文档—代码一致性检查，并把关键规格转成可执行断言。

## 6. 底座可扩展能力与长期演进

底座评估

🟢 低成本增量

【现象】Host 投影已有 status、turn、activity、revision、updatedAt。

【适合能力】等待时长显示、活动年龄、简单日志导出、状态统计、监控文案配置。

【前提】先解决数据健康度和未知状态。

🟡 中成本扩展

【现象】已有两个游戏，但没有 GameDefinition/registry 和统一命令接口。

【适合能力】更多小游戏、游戏独立设置、默认联动规则、分数持久化。

【前提】提取 GameDefinition：

id

createStore()

render()

handleSignal(signal)

serialize()/restore()

capabilities

🔴 高成本扩展

【现象】当前没有信号日志、多任务数据源、任务历史模型或规则版本。

【高成本能力】多任务对比、历史回放、跨会话统计、用户自定义规则、审批关卡解锁。

【原因】这些功能需要持久化身份、时间线、版本迁移和多 Session retention，不是继续向 client.js 添加条件分支即可完成。

最大耦合风险

🔴 全局单例锁死 Session 隔离

游戏 store、canvas、root、mode 都是模块级。

🔴 联动契约不存在

未来若直接让游戏读取 MonitorState，会形成状态级耦合，无法可靠区分“事件发生一次”和“状态持续存在”。

🟡 事件映射硬编码

endedWith()、activity kind、工具参数提示全部写死在 Host 文件。

🟡 UI 分支硬编码

两款游戏通过三元表达式切换，第三款游戏会继续复制分支。

推荐演进分层

底座加固层：Session 隔离、MonitorHealth、SignalHub、AttentionRail、兼容层、测试。

玩法扩展层：Game Registry、默认 Signal→GameCommand 映射、持久化接口。

用户自定义层：声明式规则、配置 UI、导入导出和版本迁移。

用户自定义规则只能产生游戏侧命令，例如暂停、奖励、切换关卡；规则运行时不得获得 Agent 控制接口。

边界测试用例清单

P0 必测：

新任务启动时上一轮 success 仍在投影缓存：必须立即显示“启动中/运行中”，不能继续显示成功。

running=false 先于 turn/end 到达：显示“收尾同步中”，不能无限 running，也不能猜测成功。

projection refresh 失败：显示监控不可用，不得显示 idle。

同一工具连续出现两次审批：两次都必须产生独立提醒。

审批出现时蛇正在运行：自动暂停；审批消失后仅在此前运行且无其他暂停原因时恢复。

审批出现前用户手动暂停：审批结束后仍保持暂停。

两个审批交叠：第一个结束时不能恢复，必须等最后一个审批结束。

页面滚到游戏底部后触发审批：告警仍在视口内。

会话 A 有审批，快速切到 B 再切回 A：不得在 B 显示 A 的状态或暂停 B 的游戏。

同时打开 A、B 两个 WaitBuddy 实例：游戏、焦点、canvas、设置和审批暂停互不串扰。

同一会话出现两个嵌入实例：两个画布都持续绘制，不得因 ref 覆盖冻结。

未知 turn/end.reason.kind：不得判成功。

P1 体验测试：

320px 宽、650px 高、200% 缩放：无横向滚动，审批和核心按钮可见。

超长工具名和错误信息：截断但可查看完整内容，不撑破布局。

游戏结束点击“再来一局”：一次点击直接开始。

暂停时切换速度后继续：实际速度与 UI 一致。

Chat↔WaitBuddy 切换：游戏按规则暂停并保留，监控继续跟踪。

页面隐藏、恢复、卸载、重新启用插件：计时器和监听器无残留。

1000 次 step/end：监控渲染次数受控，游戏不明显掉帧。

localStorage 禁用、数据损坏：使用默认设置且界面可用。

ResizeObserver 不可用：棋盘可玩且不越界。

reduced-motion：无无限扫光动画。

Agent 长时间无事件：显示最后活动年龄，不误判失败。

reasoning/命令含敏感参数：按配置脱敏。

演进路线规划

M0 补丁：先把“不能错过”做可靠

前置条件：

可持久化时间线；

风险：

自定义规则可能制造通知轰炸；

历史回放涉及存储体积和隐私；

审批玩法可能诱导用户为了游戏快速批准。

取舍：审批只能作为“暂停/解锁提示”，不能把批准动作游戏化、奖励化或自动化。

绝对不能做的改动（基线红线）

不能让游戏调用 Agent 的 prompt、cancel、retry、steer 或 approval.answer。

不能隐藏、替换或拦截 DSH 原生审批面板和 composer。

不能用估算百分比冒充真实任务进度。

不能在审批结束后无条件恢复游戏。

不能让一个会话的事件影响另一个会话的游戏。

不能把审批“批准”设计成游戏奖励或通关捷径。

不能在投影不可用时回退显示“空闲”。

不能将未知终态默认解释为成功。

不能无评审扩展会话事件范围，特别是 reasoning 和工具参数。

不能继续用模块级 canvas/root ref 支撑多实例。
