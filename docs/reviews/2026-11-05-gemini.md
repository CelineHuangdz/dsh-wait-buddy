### 前置总览

- **整体达标与核心风险总结**：当前仓库（`v0.3.0`）仅完成了 **M1 状态看板 + M2 独立双游戏（贪吃蛇/五子棋）**，但**完全缺失 M3「Agent 事件 → 游戏单向联动与审批自动暂停」核心闭环**；**最高优先级风险**在于当 Agent 触发工具审批（`pending_approval`）或任务完成/失败时，正在运行的贪吃蛇既不自动暂停也无画布内强提醒，极易导致用户因紧盯游戏画布而漏看或延误原生审批与任务终态。
- **底座演进潜力与最大架构瓶颈**：Host 侧基于 `sessionProjections` 纯函数 `fold` 的只读日志投影具备良好的演进基础，但 Client 侧采用**模块级全局单例 DOM 引用（`gameCanvas`/`boardEl`/`rootEl`）+ 1635 行单文件硬编码双游戏分支 + 缺失独立信号分发层（SignalBus）**，是阻碍多实例并存、新游戏扩展与自定义联动规则落地的最大架构瓶颈。

### 一、 业务 & 实际需求匹配度评审

#### 1. 🔴 严重问题：核心「审批触发自动暂停」与「Agent → 游戏单向联动」能力完全缺失（M2 越级做 M4，漏掉 M3 基线核心）

- **【现象】**：
`README.md` 与 `client.js` 明确停留在 M1+M2 阶段，`GameArea` 与 ` useMonitorState` 之间没有任何信号通道。但代码却提前合入了原本属于 M4 备选池的「五子棋（D16）」和「`localStorage` 速度/难度设置持久化（D17）」。

```
    // ---------------------------------------------------------------------
    // M2: embedded Snake game. Fully decoupled from the monitor: nothing in
    // this section reads task state, and nothing in the monitor section reads
    // game state. (Agent -> game signals arrive with M3.)
    // ---------------------------------------------------------------------
```

- **【风险/负面影响】**：
  1. **违背核心痛点初衷**：用户玩贪吃蛇（尤其是快档 `55ms–100ms`/步）时注意力高度集中在棋盘内部。当 `pending_approval` 出现时，游戏继续跑，用户要么为了保命继续盯着蛇头而错过/推迟审批，要么分神看顶部横幅导致贪吃蛇撞墙死亡，体验挫败感极强。
  2. **任务推进与游戏毫无体感关联**：`index.js` 计算了 `stepCount`（注释写明 `kept for M3 scoring`），但前端从未消费，Agent 执行了 20 步与未执行时玩游戏毫无区别，“陪伴式联动”名存实亡。
- **【可落地改进方案】**：
在 `client.js` 中补齐单向信号桥接（详见维度四方案对比）：
  - 当监控状态进入 `pending_approval` 时，若 `gameStore.getSnapshot().status === 'running'`，自动触发 `gameStore.pauseByAgent('approval')`，并在棋盘浮层展示「等待你审批工具调用，已为你自动暂停（点击继续或查看对话）」。
  - 当 `stepCount` 递增时，向游戏发送单向奖励信号（例如贪吃蛇生成限时加分果或直接获得 Agent 助力加分 `+5` 并飘字提示）。

#### 2. 🔴 严重问题：新任务启动或 Agent 异常断连时，监控状态合并逻辑（`compose`）存在状态滞留与假运行 Bug

- **【现象】**：
在 `createMonitorSource` 的 `compose()` 中，`nextStatus` 以持久化投影 `base.status` 为基准，仅当 `nextStatus === 'idle' && running === true` 时才切为 `'running'`：

```
        const base = durable === undefined ? EMPTY_STATE : durable
        let nextStatus = base.status
        if (approval !== undefined) nextStatus = 'pending_approval'
        else if (nextStatus === 'idle' && running === true) nextStatus = 'running'
        return {
          status: nextStatus,
          running: running === true,
```

- **【风险/负面影响】**：
  1. **连续多轮对话时的“旧终态闪烁/滞留”**：当第 1 轮任务处于 `success` / `failed` / `aborted` 终态，用户发起第 2 轮任务瞬间，进程内 `running` 已变为 `true`，但若 `waitbuddy` 投影尚未完成 `turn/start` 折叠同步，由于 `base.status` 是 `'failed'` 而非 `'idle'`，面板会错误保持上一轮的 `failed` 红色告警横幅和「查看对话」按钮。
  2. **Agent 进程崩溃/异常断连时的“永久假运行”**：若 Agent 在 `turn/start` 后进程崩溃或被宿主强制销毁、未写入 `turn/end` 日志，`base.status` 永久停留在 `'running'`，此时即便实时状态 `running === false`，面板仍无限期展示「正在执行任务」及脉冲动画，误导用户傻等。
- **【可落地改进方案】**：
修正 `compose()` 中实时进程状态（`running`）与日志投影状态（`base.status`）的合成优先级：

```
let nextStatus = base.status
if (approval !== undefined) {
  nextStatus = 'pending_approval'
} else if (running === true && nextStatus !== 'running') {
  // 新一轮任务已在内存中启动，但投影尚未追上 turn/start
  nextStatus = 'running'
} else if (running === false && status !== undefined && nextStatus === 'running') {
  // 实时会话明确已停止运行，但日志未收到 turn/end（如异常断连/强制中断）
  nextStatus = 'aborted'
}
```

#### 3. 🔴 严重问题：多会话分屏/多实例挂载及切会话时，全局单例 DOM 引用覆写与切会话不暂停 Bug

- **【现象】**：
  1. `gameCanvas`、`gomokuCanvas`、`boardEl`、`rootEl` 全部定义为模块级全局变量（`let gameCanvas = null`），注释假设 `only one WaitBuddy view renders at a time`。
  2. `GameArea` 组件不接收 `sessionId`，仅在组件卸载（`subscribers === 0`）时才暂停贪吃蛇。

```
    const gameStore = createGameStore()

    /** Module-scope canvas handle; only one WaitBuddy view renders at a time. */
    let gameCanvas = null

    /** Module-scope board box; used to derive the grid from its measured size. */
    let boardEl = null

    /** Stable ref callback for the board box. */
    function attachBoard(node) {
      boardEl = node
    }

    /** Module-scope view root; used to return keyboard focus to the board after a click. */
    let rootEl = null
```

- **【风险/负面影响】**：
  1. **多实例/过渡动画下画布直接死锁**：在 DSH 分屏并排打开两个会话的 WaitBuddy 视图，或宿主切换视图存在新旧实例短暂共存（新组件先 mount 赋值 `gameCanvas = node`，旧组件后 unmount 调用 `attachCanvas(null)`）时，`gameCanvas` 被置为 `null`，导致当前可见视图**彻底停止绘制画面**！
  2. **切换会话时游戏未按基线约定暂停**：当用户在会话 A 打开 WaitBuddy 玩贪吃蛇，直接点击左侧会话列表切到会话 B（会话 B 同样停留在 WaitBuddy 视图）时，`WaitBuddyView` 实例被 React 复用（仅 `props.sessionId` 变化），`GameArea` 不会卸载，`subscribers` 保持为 `1`，**贪吃蛇在会话切换瞬间继续狂奔而不暂停**，直接违反 `docs/ui-spec.md` 第 134 行「切会话 → 自动暂停并保留进度」的基线约定。
- **【可落地改进方案】**：
  1. 将 `gameCanvas`、`gomokuCanvas`、`boardEl`、`rootEl` 改为组件实例内的 `React.useRef(null)`，彻底消灭模块级 DOM 句柄。
  2. 给 `GameArea` 传入 `sessionId`，并在 `React.useEffect(() => { gameStore.pause() }, [sessionId])` 中监听会话切换，确保切换 `sessionId` 时强制暂停贪吃蛇。

#### 4. 🟡 体验缺陷：基线事件范围与展示能力存在文档/契约偏离（新增 `assistant/message` 订阅、砍掉步数展示但描述未同步）

- **【现象】**：
  - `index.js` 在基线事件外新增订阅了 `assistant/message`，提取模型 `reasoning` 明文：

```
    case 'assistant/message': {
      const reasoning = reasoningOf(event.data.message)
      if (reasoning === '') return state
      const activity = pushActivity(state.activity, 'thinking', reasoning)
      if (activity === state.activity) return state
      return { ...state, activity, updatedAt: event.time, revision: state.revision + 1 }
    }
```

- 同时，虽然 `decisions.md`（D9）决定隐藏 `stepCount`，但 `package.json`、`locale/zh.json`、`locale/en.json`、`README.md` M1 表格仍宣称展示「已完成步数」。

- **【风险/负面影响】**：
  1. 当 Agent 连续多次调用相同工具或执行无 reasoning 的步骤时，活动流因相邻去重（`pushActivity`）看起来完全静止，由于没有步数递增（如 `第 8 步`），用户无法判断 Agent 是还在推进还是卡死了。
  2. 插件商店元数据（`locale/zh.json`）与实际界面不符。
- **【可落地改进方案】**：
在右侧更新时间旁恢复轻量的非百分比步数元信息：`已完成 {stepCount} 步 · 更新于 {time}`（当 `stepCount > 0` 时显示），既遵守“不做假百分比进度”的决策 D1，又能给连续同质工具调用提供明确的存活心跳信号；同时对齐 `locale/*.json` 描述。

### 二、 使用体验（UX）评审

#### 1. 🔴 严重问题：任务完成/失败/待审批时缺乏画布内联动反馈，且顶部横幅插入引发画布跳动误触

- **【现象】**：
  - 告警横幅 `AlertBanner` 采用文档流条件渲染在 `.wb-inner` 最顶部（`client.js:1401-1427`）。
  - 任务变为 `success` 时，没有任何横幅或画布提示，且状态圆点 `.wb-dot[data-state="success"]` 与 `.wb-dot[data-state="running"]` 使用了**完全相同的绿色变量** `--dsw-alias-state-success-primary`（`client.js:1443-1445`）。

- **【风险/负面影响】**：
  1. **布局跳动导致五子棋落子误触**：当用户正在五子棋棋盘上点击交叉点落子时，若恰好触发 `pending_approval` 或 `failed`，顶部突然插入高约 `38px` + `16px` 间距的 `.wb-alert`，整个棋盘瞬间向下跳动 `54px`，导致鼠标点偏到错误交叉点（且五子棋不支持悔棋！）。
  2. **任务完成了用户却浑然不知**：运行态和成功态圆点同为绿色，用户视线聚焦在下方 480px 高的棋盘时，顶部 `2px` 脉冲条消失和文字变化处于视觉余光盲区，极易出现“任务早已跑完，用户还在埋头下棋”的反客为主现象。

- **【可落地改进方案】**：
  - **方案 A（推荐：固定状态槽位 + 画布内非阻塞 Toast/遮罩联动）**：
    1. 将 `.wb-dot[data-state="running"]` 改为品牌蓝/进行中色（如 `--dsw-alias-brand-primary`），与 `success` 的绿色拉开区分。
    2. `pending_approval` 时自动暂停贪吃蛇，并在游戏浮层（`.wb-overlay`）同步显示醒目的审批提醒与「切回对话处理」快捷入口。
    3. 任务进入终态（`success` / `failed` / `aborted`）瞬间，在棋盘顶部边缘弹出一个持续 4 秒的半透明胶囊 Toast（如 `🎉 当前会话任务已完成 · 点击查看对话`），不打断五子棋残局但确保视线焦点内必达。
  - **方案 B（预留固定高度告警占位区）**：
    始终为告警区域预留固定高度避免棋盘位移，但空闲/正常运行时会浪费宝贵的 `48px` 垂直空间，在小窗口下挤压棋盘，故**推荐方案 A**。

#### 2. 🟡 体验缺陷：贪吃蛇单步方向覆盖 Bug（单 Tick 内快速连按两键导致自杀）

- **【现象】**：
`turnGame` 只用单个 `nextDir` 字段缓存方向，且判断反向时拿 `state.nextDir`（而非当前步实际移动方向 `state.dir`）做对比：

```
    function turnGame(state, dir) {
      if (state.status !== 'running') return state
      const current = state.nextDir === null ? state.dir : state.nextDir
      if (dir === current || dir === OPPOSITE[current]) return state
      return { ...state, nextDir: dir }
    }
```

- **【风险/负面影响】**：
在慢速（`200ms`/步）或标准速度（`140ms`/步）下，当蛇向右移动（`dir = 'right'`）时，玩家在同一个 tick 周期内快速按 `↑` 再按 `←` 进行拐弯：
  1. 按 `↑`：`current` 为 `'right'`，`nextDir` 变为 `'up'`；
  2. 按 `←`（仍在同一 tick 内）：`current` 取了 `nextDir`（`'up'`），`'left'` 与 `'up'` 不相反，于是 `nextDir` 被覆盖为 `'left'`；
  3. 下一帧 `tickGame` 执行时，蛇从 `'right'` 直接变成 `'left'`，一头撞上自己的脖子（`hitSelf = true`）瞬间暴毙！这是贪吃蛇玩家最抓狂的手感缺陷。
- **【可落地改进方案】**：
将 `nextDir: string | null` 改为最多容纳 2 个指令的输入队列 `dirQueue: string[]`：

```
function turnGame(state, dir) {
  if (state.status !== 'running') return state
  const queue = state.dirQueue || []
  if (queue.length >= 2) return state
  const lastDir = queue.length > 0 ? queue[queue.length - 1] : state.dir
  if (dir === lastDir || dir === OPPOSITE[lastDir]) return state
  return { ...state, dirQueue: [...queue, dir] }
}
```

并在 `tickGame` 中每次消费 `dirQueue[0]`，保留 `dirQueue.slice(1)`，即可完美支持快速 180° U 型连拐且绝不自撞。

#### 3. 🟡 体验缺陷：贪吃蛇交互细节断裂（「再来一局」需点两次、暂停态改速度不生效、底部按钮丢焦点、缺空格键暂停）

- **【现象】**：
  1. `gameOverlay` 在 `state.status === 'over'` 时，「再来一局」按钮调用的是 `gameStore.reset()`（回到 `idle` 态）而非 `gameStore.start()`（`client.js:767`），用户点了「再来一局」后又弹出「开始游戏」，必须连点两次才能开局。
  2. `gameStore.setSpeed`（`client.js:569-576`）仅在 `state.status === 'running'` 时更新 `tickMs`；若在 `paused` 或 `idle` 态切换速度，恢复游戏后仍沿用旧速度。
  3. `setGrid`（`client.js:558-562`）重建网格时调用 `createGameState(state.best, cols, rows)` 未传入当前速度，导致 `settingsStore` 中持久化的速度在首次挂载测量尺寸后被重置回 `'normal'`。
  4. 点击底部控制栏的「暂停 / 继续 / 重置」按钮（`client.js:1338, 1347`）未调用 `focusRoot()`，且点击「重置」后「暂停」按钮变为 `disabled` 导致焦点落回 `document.body`，方向键失灵。

- **【风险/负面影响】**：
操作链路处处卡顿，用户频繁遇到“点了再来一局没开始”、“调了速度没反应”、“点了继续后按方向键蛇不动”的体验故障。

- **【可落地改进方案】**：
  1. `over` 浮层的「再来一局」改为直接调用 `gameStore.start(settingsStore.getSnapshot().speed)`。
  2. `setSpeed` 根据已吃果实数按新档位公式重算 `tickMs`，无论当前是 `running`、`paused` 还是 `idle` 均同步更新：

```
  const eaten = Math.floor(state.score / FOOD_SCORE)
  const preset = SPEED_PRESETS[speedId]
  const nextTickMs = Math.max(preset.min, preset.start - eaten * preset.step)
```
  3. `setGrid` 传入 `state.speed`；底部操作按钮点击后统一调用 `focusRoot()`；`onGameKeyDown` 补充 `Space` 键切换暂停/继续与 `WASD` 方向键支持。

#### 4. 🟡 体验缺陷：五子棋电脑瞬时同步落子，玩家缺乏落子反馈与最后一步区分

- **【现象】**：
`placeGomoku`（`client.js:944-967`）在同一次点击事件中同步写入黑子（玩家）和白子（AI），且棋盘仅用红点标记 `state.lastMove`（永远停在白子上）。

- **【风险/负面影响】**：
玩家点击瞬间画面直接蹦出两颗棋子，当 AI 落子位置距离玩家较远（如防守另一侧）时，玩家瞬间找不到AI刚下在哪、自己刚下在哪，视觉极度突兀。

- **【可落地改进方案】**：
  1. 在 `gomokuState` 中同时记录 `lastHumanMove`（用细蓝圈/绿点标记）与 `lastAiMove`（用红点标记）。
  2. 将 AI 落子延迟 `120ms–180ms`（在 `gomokuStore` 中加 `thinking: true` 锁并在 `dispose`/重置时清理 `setTimeout`），让玩家先看到黑子落下，再看到白子回应，弈棋节奏自然清晰。

- **【风险/负面影响】**：

- **【可落地改进方案】**：
  1. `.wb-alert` 增加 `flex-wrap: wrap`，允许窄屏下 `.wb-alertMeta` 换行显示完整工具名/错误摘要。

#### 2. 🟡 体验缺陷：五子棋窗口缩放不重绘（缺失 `ResizeObserver`）且终局遮罩与方形棋盘错位

#### 3. 🟢 优化改进：主次视觉权重失衡与脉冲条语义色冲突

### 四、 数据联动 & 事件订阅架构评审（重点）

#### 1. 🔴 严重问题：首次打开会话视图时，异步投影拉取（`ensureProjection`）后未重新绑定 `face.subscribe`

- **【现象】**：
在 `createMonitorSource` 的 `start()` 中（`client.js:262-277`）：

```
      /** Ask the controller once for a fresh projection read when the key is still missing. */
      const ensureProjection = () => {
        if (refreshRequested || readDurable() !== undefined) return
        refreshRequested = true
        try {
          const pending = ctx.sessions.refreshProjections(sessionId)
          if (pending !== undefined && typeof pending.catch === 'function') {
            pending.catch((error) => console.error('[wait-buddy] projection refresh failed', error))
          }
        } catch (error) {
          console.error('[wait-buddy] projection refresh failed', error)
        }
      }

      const start = () => {
        ensureProjection()
        const disposersNext = []
        const binding = bindingOf()
        if (binding !== undefined) {
          const face = binding.session.projections.faceOf('waitbuddy')
          if (face !== undefined) disposersNext.push(face.subscribe(refresh))
          disposersNext.push(binding.session.subscribe(refresh))
        }
```

- **【风险/负面影响】**：
当会话刚创建或首次激活 `waitbuddy` 投影时，`start()` 执行瞬间 `bindingOf()` 或 `faceOf('waitbuddy')` 可能尚为 `undefined`。此时 `ensureProjection()` 异步调用了 `ctx.sessions.refreshProjections(sessionId)`，但在 Promise 完成后**既没有调用 `refresh()`，也没有检查并补订 `face.subscribe(refresh)`**！这会导致冷启动会话的投影数据拉取回来后，由于没有挂上 `face` 监听器，后续 `waitbuddy` 投影的增量更新无法触发视图刷新。
- **【可落地改进方案】**：
在 `refresh()` 及 `ensureProjection().then()` 中动态检查 `faceOf('waitbuddy')` 是否已就绪，若尚未订阅则惰性补齐 `face.subscribe(refresh)` 并加入 `disposers`：

```
let subscribedFace = null
const ensureFaceSubscription = () => {
  const binding = bindingOf()
  const face = binding?.session?.projections?.faceOf('waitbuddy')
  if (face !== undefined && face !== subscribedFace) {
    subscribedFace = face
    disposers.push(face.subscribe(refresh))
  }
}
```

在 `start()`、`refresh()` 以及 `refreshProjections(sessionId).then(...)` 中均调用 `ensureFaceSubscription()`。

#### 2. 🔴 严重问题：监控层与游戏层之间缺失「独立信号分发层（SignalBus）」，尚未实现解耦式单向联动

- **【现象】**：
基线要求「监控信号层与游戏逻辑解耦：监控产生的信号独立，游戏只消费信号，不反向侵入 Agent 任务逻辑」。当前代码之所以“互不依赖”，是因为**根本没写信号层**。

- **【风险/负面影响】**：
如果在补齐 M3 时直接在 `WaitBuddyView` 或 `createMonitorSource` 里硬编码调用 `gameStore.pause()` / `gameStore.addBonus()`，就会把监控数据源和贪吃蛇状态机焊死在一起，违反基线解耦约束，且后续五子棋或新游戏无法接入。

- **【可落地改进方案（多方案对比）】**：
  - **方案 A（推荐：轻量级单向 `SignalBus` + 边沿触发器 `SignalEmitter`）**：
    - 在监控层之上增加纯函数边沿检测器 `diffMonitorSignals(prev, next)`，仅当 `prev.ready && next.ready`（排除首次挂载历史快照回放！）且状态发生跃迁时，向 `SignalBus` 派发标准语义信号：
      - `{ type: 'agent:task_start', turn }`
      - `{ type: 'agent:step_advance', delta, stepCount }`
      - `{ type: 'agent:approval_enter', toolName }`
      - `{ type: 'agent:approval_leave' }`
      - `{ type: 'agent:task_finish', status }`
    - 游戏 Store 通过注册 `signalBus.subscribe(onSignal)` 自主决定如何消费信号（如贪吃蛇收到 `agent:approval_enter` 自动暂停、收到 `agent:step_advance` 触发加分果；五子棋收到 `agent:approval_enter` 仅展示提示条）。
    - **优点**：零耦合、天然过滤首次打开视图时的历史状态误触发、支持任意多款游戏按需订阅、完全单向（无返回值）。
    - **缺点**：需增加约 40 行信号转换与去重代码。
  - **方案 B（在 React 组件层用 `useEffect` 监听 `state` 直接调 `gameStore` 方法）**：
    - **优点**：改动最少（约 15 行）。
    - **缺点**：视图组件与具体游戏 Store 强耦合；切换会话或首次挂载极易把历史快照当成新事件误触发奖励；无法扩展自定义映射规则。
  - **结论**：**强烈推荐方案 A**。

#### 3. 🟡 体验缺陷：Host 侧 `fold` 对乱序/非运行态事件缺少 `turn` 与 `status` 守卫，且错误文案在服务端硬编码中文

- **【现象】**：
  1. `index.js` 中 `step/end` 校验了 `if (state.status !== 'running' || event.data.turn !== state.turn) return state`，但 `assistant/message`、`tool/call`、`turn/end` **均未校验 `state.status` 和 `event.data.turn`**（`index.js:208-230`）。
  2. `endedWith` 将 `'模型请求失败'`、`'本轮达到模型输出上限'`、`'本轮被阻止，未继续执行'` 直接硬编码为中文字符串存入持久化投影 `state.errorMessage`（`index.js:160-168`）。

- **【风险/负面影响】**：
  1. 当任务被中断（`aborted`）后若有滞后的工具输出或子代理消息写入日志，`activity` 和 `updatedAt` 会在终态下被意外篡改。
  2. 当用户将 DSH 切换为英文（`en`）时，面板会出现 `Task failed · 本轮达到模型输出上限` 的中英混杂脏数据，且因为已写入持久化投影缓存，切换语言也无法修复。

- **【可落地改进方案】**：
  1. 在 `assistant/message` 和 `tool/call` 分支加上 `if (state.status !== 'running') return state` 守卫；在 `turn/start`、`step/end`、`turn/end` 对 `event.data?.turn` 和 `event.time` 做安全兜底（`typeof event.time === 'number' ? event.time : Date.now()`），防止异常日志结构触发 Zod `stateSchema` 校验崩溃。
  2. 将 `endedWith` 拆分为结构化 `errorKind: 'error' | 'max-tokens' | 'blocked' | ''` + 原始 `errorMessage`，在 Client 端通过 `t('error.maxTokens')` 等字典键进行本地化渲染。

### 五、 代码 & 插件工程质量（DSH 插件规范）评审

#### 1. 🔴 严重问题：模块加载期副作用与 Cordis 插件重载（HMR / 启停）生命周期不一致，存在内存泄漏与失效隐患

- **【现象】**：
`gameStore` 在模块顶层（`window.__ModuleLoader__.load` 工厂函数执行时）立即创建并绑定了全局 `document.addEventListener('visibilitychange', onVisibility)`（`client.js:540, 585`），而在 `apply(ctx)` 中注册了 `ctx.effect(() => () => gameStore.dispose())`（`client.js:1588`）。

```
      const onVisibility = () => {
        if (document.hidden && state.status === 'running') set(pauseGame(state))
      }
      document.addEventListener('visibilitychange', onVisibility)
```

```
      apply(ctx) {
        clientCtx = ctx
        ctx.effect(() => () => gameStore.dispose(), 'wait-buddy: snake loop')
        const t = ctx.locale.bind(NS)
```

- **【风险/负面影响】**：
根据 Cordis 插件机制（同一个 `Plugin.Runtime` 的 `apply` 函数在插件停用再启用、`fiber.restart()` 配置重载时会再次执行，但模块文件本身不会重新加载）：
  1. 插件第一次停用时，`ctx.effect` 清理函数调用 `gameStore.dispose()`，移除了 `visibilitychange` 监听。
  2. 插件再次启用时，`apply(ctx)` 重新执行，但顶层的 `createGameStore()` 不会再跑，`visibilitychange` 监听永远丢失！
  3. 停用时 `clientCtx` 未在 `effect` 清理函数中置回 `null`，残留已销毁 Fiber 的旧 `ctx` 引用。
- **【可落地改进方案】**：
将 `visibilitychange` 监听器的绑定/解绑移入 `gameStore.subscribe`（当 `subscribers` 从 `0 -> 1` 时 `addEventListener`，从 `1 -> 0` 时 `removeEventListener`），并在 `apply(ctx)` 的 `ctx.effect` 卸载回调中执行 `clientCtx = null; gameStore.dispose()`。

#### 2. 🟡 体验缺陷：高频事件与贪吃蛇 Tick 下的 불필요한 React 整棵组件树重渲染

- **【现象】**：
  1. `GameArea` 订阅了 `gameStore`（`client.js:1196-1200`），贪吃蛇运行时每 `55ms–140ms`（每秒 7~18 次）都会调用 `setSnake(gameStore.getSnapshot())`。
  2. 每次 `setSnake` 都会触发整个 `GameArea` 的 React VDOM 重新渲染（重建所有分段按钮、设置项、底部按钮、Canvas 属性），仅仅为了在 `useEffect` 中调用 `drawGame(gameCanvas, snake)`！
  3. 同时，`WaitBuddyView` 每次收到监控状态更新时，由于 `GameArea` 未使用 `React.memo`，也会连带触发 `GameArea` 重渲染；而 `createMonitorSource` 订阅了全局 `uiSession.sessionStatus`（所有会话共享的 Map），其他后台会话的状态变化也会高频触发当前会话的 `refresh()`。

- **【风险/负面影响】**：
当 Agent 高频输出流式消息或后台有多个会话并行运行时，叠加贪吃蛇 18Hz 的 React 状态刷新，会在低配机器或长时间运行后造成主线程无效 GC 与 UI 掉帧。

- **【可落地改进方案】**：
  1. **Canvas 绘制与 React UI 状态分离**：在 `GameArea` 的 `useEffect` 中直接订阅 `gameStore.subscribe(() => drawGame(canvasRef.current, gameStore.getSnapshot()))` 进行命令式绘制；React 的 `useState` 仅在 `status`、`score`、`best`、`speed` 发生变化时才触发重渲染（普通移动帧零 React 渲染开销！）。
  2. 使用 `React.memo(GameArea)` 隔离监控面板刷新对游戏区的无效重绘。

#### 3. 🟡 体验缺陷：导出了 `__game` 测试接口但仓库内零自动化测试，且文档与代码多处漂移

- **【现象】**：
  - `client.js:1613` 专门导出了 `__game` 对象注释用于单元测试，但仓库内没有任何测试文件，`package.json` 也没有 `test` 脚本。
  - `docs/decisions.md` D6 规定“先改文档，再改代码；实现必须与文档一致”，但 `README.md` 仍写着 `高度 min(40vh, 360px)`、`已完成步数`、`软按钮`，`docs/ui-spec.md` 第 10 行写 `min(40vh, 360px)` 而第 35 行写 `min(46vh, 480px)`。

- **【风险/负面影响】**：
没有自动化回归测试保障，`fold` 状态机、贪吃蛇快速连按反向、五子棋胜负判定等纯逻辑修改极易引入回归问题；文档前后矛盾降低交接可信度。

- **【可落地改进方案】**：
使用 Node.js 原生测试运行器（`node --test`，无需引入额外 devDependencies）编写针对 `index.js`（`fold` 状态机）与 `client.js`（`__game` 导出函数）的单元测试，并在 `package.json` 加入 `"test": "node --test"`。

#### 2. 耦合风险与演进分层设计

当前代码将「监控数据源」、「UI 状态看板」、「贪吃蛇引擎」、「五子棋引擎」、「持久化设置」全部平铺在 `client.js` 同一个闭包内。为避免后续迭代锁死，建议按三层解耦演进：

1. **L1 底座加固层（Monitor & Signal Core）**：Host `waitbuddy` 投影 + Client `createMonitorSource` + 边沿触发 `SignalBus`。职责：只管产出可靠的 `TrackState` 和单向 `AgentSignal`，绝对不知道任何游戏的存在。
2. **L2 玩法扩展层（Game Adapter Registry）**：定义标准协议 `{ id, labelKey, mount, unmount, pause, resume, reset, onSignal, renderSetting, renderControls }`。贪吃蛇、五子棋及未来的 2048 均作为独立 Adapter 注册，消除 `if (mode === 'snake')` 硬编码。
3. **L3 用户自定义层（Settings & Rule Mapper）**：管理 `localStorage` 偏好及 `AgentSignal -> GameEffect` 的映射配置。

#### 3. DSH 宿主依赖风险梳理与兼容预案

| 依赖项 | 所在位置 | 稳定性风险等级 | 失效影响与兼容预案 |
| --- | --- | --- | --- |
| `ctx.get('uiSession').sessionStatus` | `client.js:194, 271` | 🔴 高风险（未在 `inject` 声明的内部状态） | 若 DSH 升级调整 `pendingInteraction` 字段结构，审批提醒将静默失效。**预案**：增加可选链与结构嗅探，并在 `uiSession` 晚期注入时支持重绑。 |

### 七、 边界测试用例清单（用于验证修复效果）

请在修复后逐条执行以下 8 个高危边界用例：

1. **【审批打断贪吃蛇测试】**：将贪吃蛇调至「快」档并开始游戏 → 触发需要审批的 Agent 工具调用（如执行危险命令） → **预期**：贪吃蛇立即自动暂停，浮层提示「等待审批中，已自动暂停」，不发生撞墙 Game Over；在原生弹窗完成审批后，可一键继续原局。
2. **【五子棋落子防跳动测试】**：在五子棋对局中，当 Agent 刚进入 `pending_approval` 或 `failed` 触发顶部横幅出现/消失瞬间，点击棋盘交叉点 → **预期**：棋盘无垂直跳动或点击坐标准确，不发生错位落子。
3. **【贪吃蛇单步双键防自杀测试】**：贪吃蛇调至「慢」档（`200ms`），向右移动时在 `100ms` 内快速连按 `↑` + `←` → **预期**：蛇先向上走一格、下一格再向左拐，绝不原地反向自撞暴毙。
4. **【多会话快速切换与分屏多实例测试】**：
   - 场景 4a：在会话 A 启动贪吃蛇后，点击侧边栏快速切换到会话 B、会话 C 再切回会话 A → **预期**：切走瞬间贪吃蛇立即变更为 `paused`，且各会话顶部的监控状态、活动流严格隔离，无残留上一会话的错误横幅。
   - 场景 4b：在 DSH 分屏模式下同时打开两个 WaitBuddy 视图，然后关闭其中一个分屏 → **预期**：剩余分屏的贪吃蛇/五子棋画布继续正常绘制，不出现画布冻结。
5. **【连续轮次（Turn #1 失败 → Turn #2 启动）状态重置测试】**：让第 1 轮任务执行失败（出现红色失败横幅与「查看对话」按钮） → 立即发起第 2 轮新任务 → **预期**：在 `running === true` 瞬间，旧的红色失败横幅与「查看对话」按钮立即消失，状态切换为「正在执行任务」，活动流清空。
6. **【Agent 异常断连/强制中断兜底测试】**：在 Agent 执行长任务中途强制中断或模拟进程停止（`running` 变为 `false` 但无 `completed`） → **预期**：面板立即退出 `running` 脉冲态，切换为 `任务已中断`，不发生永久“正在执行任务”假死。
7. **【窗口缩放与五子棋重绘测试】**：在五子棋下了 6 手后，拖拽缩放 DSH 窗口宽度与高度 → **预期**：五子棋棋盘始终保持正方形等比清晰重绘，红点/棋子不变形，点击交叉点命中准确。
8. **【中英双语切换与异常错误文案测试】**：触发 `max-tokens` 或 `error` 失败后，将 DSH 界面语言切换为英文（`en`） → **预期**：失败横幅与状态文案全部显示英文，不出现硬编码中文残留。

### 八、 演进路线规划（M0 补丁 → M1 能力扩展 → M2 自定义生态）

#### 阶段 1：M0 稳定性与基线闭环补丁（当前最优先）

- **目标**：修复所有 🔴 严重问题与核心 🟡 体验缺陷，补齐「审批自动暂停 + Agent 事件单向信号层」，消除多实例 DOM 引用覆写与状态合成 Bug。
- **依赖前置条件**：无，完全基于现有 DSH `0.2.1-rc.5` API。
- **风险**：首次引入 `pending_approval` 自动暂停时，需注意区分“Agent 触发的自动暂停”与“用户手动点击的暂停”，避免审批结束后错误自动恢复用户原本手动暂停的棋局。
- **取舍**：本阶段不做复杂游戏特效，优先保证「审批零漏看、切会话必暂停、画布零死锁」。

#### 阶段 2：M1 能力扩展与架构解耦（短期迭代）

- **目标**：
  1. 落地 `SignalBus` + `GameAdapter` 注册表，彻底解耦 `GameArea` 中的硬编码双游戏分支；
  2. 升级 Host 投影 `stateVersion: 3`，增加 `turnStartedAt`、实时已等待时长计时、已完成步数展示与结构化 `errorKind` 国际化；
  3. 增加任务完成/失败时的画布内轻量 Toast 提醒与贪吃蛇步骤加分果联动。
- **依赖前置条件**：阶段 1 的 React `useRef` 改造与状态合成修复完成。
- **风险**：升级 `stateVersion: 3` 会使升级插件时的旧会话投影缓存重算一次（符合 DSH `sessionProjections` 预期机制）。
- **取舍**：只统计当前会话实时与累计等待时长，暂不做跨会话全局统计看板。

#### 阶段 3：M2 自定义生态与高阶玩法（中远期规划）

- **目标**：
  1. 支持用户在面板中自定义「Agent 信号 → 游戏反馈」映射规则（如静默模式、仅审批暂停、步骤加速/加分）；
  2. 探索只读式「审批关卡解锁」玩法（原生审批完成后解锁五子棋悔棋次数或贪吃蛇护盾道具）；
  3. 按需通过 `GameAdapter` 接入第 3 款轻量游戏（如 2048）与等待日志导出。
- **依赖前置条件**：阶段 2 的 `SignalBus` 与 `GameAdapter` 接口稳定运行。
- **风险**：过多配置项会破坏面板“一屏极简”的设计原则。
- **取舍**：配置项收拢在折叠弹出层中，绝不增加主界面常驻高度。

### 九、 总结清单：红线边界与落地优先级

#### 🚫 【绝对不能做的改动（基线红线）】

1. **严禁反向控制 Agent 任务**：插件内绝不能提供「取消任务」、「重试任务」、「修改 Prompt」或「在游戏面板内直接点击通过/拒绝工具审批」的写操作接口。
2. **严禁遮挡、劫持或延迟 DSH 原生审批弹窗**：不得注册或 shadow `conversation.composer.*` 等审批/输入核心槽位，不得用全屏模态框遮挡宿主界面。
3. **严禁让小游戏视觉与交互优先级凌驾于监控告警之上**：出现 `pending_approval` 或 `failed` 时，必须优先保障告警可见性与游戏自动退让（自动暂停），绝不允许为了游戏连贯性而忽略或延迟审批提示。
4. **严禁在 Host 投影 `fold` 中产生副作用**：`index.js` 的 `fold` 必须保持 100% 纯函数与幂等，不得写会话日志、不得发网络请求、不得依赖外部可变状态。

#### ✅ 【推荐优先落地的 M0 迭代清单】（建议本轮立即修复）

1. **[🔴 必修]** 实现 `pending_approval` 自动暂停贪吃蛇并在棋盘浮层展示审批提醒 +「查看对话」入口。
2. **[🔴 必修]** 移除 `client.js` 中 `gameCanvas`、`gomokuCanvas`、`boardEl`、`rootEl` 四个模块级全局 DOM 变量，改为组件内 `useRef`；在 `GameArea` 监听 `sessionId` 变化自动暂停游戏。
3. **[🔴 必修]** 修复 `createMonitorSource` 的 두处核心缺陷：① `compose()` 中 `running === true` 覆盖上一轮残留终态、`running === false` 兜底异常断连；② `ensureProjection()` 异步完成后补绑 `face.subscribe(refresh)`。
4. **[🟡 必改]** 修复贪吃蛇单 tick 双键自杀 Bug（改用长度 2 的 `dirQueue`）、修复「再来一局」需点两次、修复暂停态改速度不生效、补齐 `Space` 暂停与按钮点击后 `focusRoot()`。
5. **[🟡 必改]** 为五子棋补齐 `ResizeObserver` 重绘与正方形容器约束（`aspect-ratio: 1/1`），消除终局遮罩错位；修复窄窗口下 `.wb-alert` 文字挤压溢出。
6. **[🟡 必改]** 在 `index.js` 为 `assistant/message` 与 `tool/call` 补齐 `state.status === 'running'` 守卫，并将硬编码中文错误文案改为结构化枚举交由 Client 国际化。

#### 🔭 【M1 远期规划建议】
